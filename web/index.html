01 · 제품의 핵심

Cypher가 들어가고, 플래너가 최적화하는 SQL이 나옵니다.

02 · 특장점

      

        
여섯 가지가 구조적으로 다릅니다. 상수배가 아니라 설계가 다릅니다.

        

          아래 항목은 기능 목록이 아니라 저장 구조와 컴파일 경로의 귀결입니다.
          그래서 규모가 커질수록 격차가 벌어집니다.
        

      

    


    

      

        Storage
        
인접 리스트를 CSR 세그먼트로 묶습니다

        

          한 노드의 이웃 최대 256개를 정렬된 int8[] 두 개에 담아 하나의 힙 튜플에 넣습니다.
          4 KB — 8 KB 페이지 하나에 들어갑니다. 차수 256 이하 노드 확장은 튜플 읽기 한 번입니다.
          엣지 하나당 한 행 + B-tree 탐색 + 랜덤 힙 페치를 반복하는 방식과는 접근 횟수 자체가 다릅니다.
        

        
og_adj (src, etype, dir, seq, nbr int8[], eid int8[])
STORAGE MAIN — TOAST 밖으로 밀려나 지역성을 잃지 않도록

      


      

        Properties
        
속성은 JSON 블롭이 아니라 진짜 타입 컬럼입니다

        

          타입 카탈로그가 타입마다 테이블을 생성하고, 선언된 속성은 실제 컬럼이 됩니다.
          컬럼 프루닝, 컬럼별 통계, CHECK 제약, 유니크 인덱스, HNSW 인덱스가 공짜로 따라옵니다.
        

        

          선언하지 않은 속성은 __ext jsonb로 떨어져 스키마리스 사용도 그대로 됩니다 —
          다만 빠른 경로를 받지 못합니다. 올바른 인센티브입니다.
        

        
og_data.n_4 (id int8 PK, p_model text, p_year int4, __ext jsonb)

      


      

        Type system
        
상속이 실제로 상속됩니다

        

          MATCH (v:Vehicle) 하나로 Car와 EV가 함께 답합니다.
          두 번째 라벨을 손으로 관리하는 사람은 없습니다.
        

        

          하위 타입 판정은 구간 라벨(interval label) 범위 비교 한 번입니다 — 재귀 순회가 아닙니다.
          계층이 얼마나 깊든 넓든 비용은 같습니다. 다중 상속은 경로마다 라벨 행을 하나씩 갖고, 판정은 여전히 범위 비교입니다.
        

        
Vehicle.lft ≤ EV.lft AND EV.rgt ≤ Vehicle.rgt
회귀 테스트가 상위타입 질의 플랜에 Recursive 노드가 없음을 단언합니다

      


      

        Roles
        
관계에 역할(role)과 제약이 있습니다

        

          문자열 타입 관계로는 표현할 수 없는 것 — 관계 타입이 이름 붙은 참여자 슬롯을 선언하고,
          데이터베이스가 직접 거부합니다. n항 관계도 ordinal 2+로 표현됩니다.
        

        

          transitive / symmetric / reflexive / inverse 특성도 선언합니다.
        

        
ERROR: role 'owner' of relation 'OWNS'
       requires a 'Person', got 'EV'

      


      

        Vectors
        
임베딩이 관계 위에도 있습니다

        

          임베딩은 vector(N) 타입 속성 = 타입 테이블의 컬럼입니다.
          엣지 타입에도 노드 타입과 정확히 동일하게 붙습니다.
        

        

          그 한 가지 결정에서 전부 따라옵니다 — HNSW는 그 컬럼의 평범한 인덱스이고, MVCC와 RLS가 그대로 적용되며,
          그래프 술어가 ANN 인덱스와 같은 릴레이션에 떨어지므로 필터 푸시다운이 구조적으로 보장됩니다.
          사후 필터가 숨을 곳이 없습니다.
        

        
og_add_embedding('kb','CITES','context_emb',1536,'cosine','note')
og_hybrid_search(...) — 벡터 순위 + 그래프 근접도 RRF 융합

      


      

        Interop
        
RLS가 순회 도중에 적용됩니다

        

          컴파일된 질의는 평범한 테이블을 읽습니다. 그래서 호출자가 볼 수 없는 노드는 조인되지 않고,
          그 노드를 지나는 모든 경로가 결과에서 사라집니다. 적용 코드가 한 줄도 없습니다 —
          포크가 아니라 확장이기 때문에 생기는 배당금입니다.
        

        

          기존 테이블은 og_map_table()로 복사 없이 노드 타입으로 노출하고,
          결과는 og_cypher_json()을 PostgREST RPC로 그대로 씁니다.
        

        
og_enable_rls(graph, type, policy_expr)
og_node_view · og_edge_view · og_type_view

03 · 벤치마크

      

        
수치는 그 근거만큼만 값어치가 있습니다. 그래서 하네스를 우리에게 적대적으로 짰습니다.

        

          동일 데이터 · 동일 기계. 결정론적 엣지 생성기 하나가 그래프를 만들고,
          각 시스템은 자기 벌크 경로로 적재합니다. 기계 간 비교는 하지 않습니다.
          모든 시스템이 같은 논리 질의를 돌리고, 답이 다르면 하네스가 불일치를 출력한 뒤 그 측정치를 무효(void) 처리합니다.
          이건 형식적인 절차가 아닙니다 — 개발 중 실제 불일치를 잡아냈고, 그 이전 수치는 전부 무의미했습니다.
        

        

          각 시스템에는 그 시스템 문서가 만들라고 하는 인덱스를 전부 만들어 줍니다.
          AGE는 설치 상태 그대로면 엣지 끝점에도 속성에도 인덱스가 없습니다 — 그 상태로 재면
          데이터베이스가 아니라 설정 실수를 재는 것입니다. 권장 인덱스를 붙이자 AGE의 1홉은
          29.6 ms에서 1.6 ms로, 속성 스캔은 12.1 ms에서 0.27 ms로 내려갔습니다.
          같은 기준을 우리에게도 적용해 og_create_index를 붙였습니다.

4홉을 넘기면 우리가 하던 일은 순회가 아니었습니다. 경로 열거였습니다.

03.3 · 무엇을 바꿨나

      

        
저장 구조는 그대로입니다. 컴파일러가 질문을 다시 읽을 뿐입니다.

        

          새 인덱스도, 새 테이블도, 새 문법도 없습니다. Cypher가 뜻하는 바도 바뀌지 않았습니다.
          컴파일러가 경로를 관측할 수 있는 질의인지 판정하고, 관측할 수 없을 때만
          경로 열거 대신 방문 집합 BFS(og_reach)를 내보냅니다.
        

      

    


    

      

        
          
질의컴파일 결과이유

        
        
          

            -[:K*1..8]->(b) RETURN count(DISTINCT b)
            og_reach중복 행이 답을 바꿀 수 없음
          

          

            -[:K*1..8]->(b) RETURN DISTINCT b.name
            og_reach같음
          

          

            -[:K*1..8]->(b) RETURN count(b)
            og_vlp경로 수를 세는 질문 — 답이 달라짐
          

          

            MATCH p = (a)-[:K*1..8]->(b)
            og_vlp경로 변수를 묶음
          

          

            -[e:K*1..8]->(b) RETURN count(DISTINCT b)
            og_vlp관계 변수를 묶음
          

          

            -[:K*1..2]->(b) RETURN count(DISTINCT b)
            og_vlp얕아서 바꾸면 손해 — 아래 설명
          

        
      

    

    

      마지막 줄이 이 변경에서 가장 많이 배운 지점입니다.
      og_reach는 Rust 집합 반환 함수라
      og_vlp(SQL 함수)와 달리 주변 플랜에 인라인되지 않고 레벨마다 SPI 비용을 냅니다.
      첫 구현은 조건 없이 바꿨고, 2홉에서 1.9 ms → 4.9 ms로 더 느려졌습니다.
      그래서 교차점을 계산합니다 — Σ degreei > |V|,
      즉 걸어야 할 경로 수가 찾을 노드 수를 넘는 지점. 두 값 모두 플래너 통계에서 읽으므로
      스캔 한 번 하지 않습니다. 5만 노드/차수 20에서는 3홉에 「아니오」, 4홉에 「예」가 나오고,
      측정된 교차점과 정확히 일치합니다.

04 · 에이전트 네이티브

      

        
LLM이 틀리는 방식은 사람과 다릅니다. 그건 프롬프트가 아니라 데이터베이스가 고칠 문제입니다.

        

          에이전트는 없는 라벨을 지어내고, 화살표를 뒤집고, 실수로 카티션 곱을 씁니다 — 아주 확신에 차서.
          그래서 이 표면은 스스로 교정하는 루프로 설계했습니다. 모든 단계가 평범한 SQL 호출입니다.
        

      

    


    

      

        og_schema_for(graph, question)
        
DDL 말고 스키마를 주십시오

        

          질문에 관련된 부분만, 토큰 예산에 맞춰 돌려줍니다. roles 필드가
          화살표가 어느 쪽을 향하는지를 알려줍니다 — 생성된 Cypher에서 가장 흔한 버그가 그겁니다.
          예산 때문에 잘렸다면 잘렸다고 명시합니다. 스키마가 부분적임을 아는 모델은 되묻고, 모르는 모델은 지어냅니다.
        

      

      

        og_estimate(graph, query)
        
돌리기 전에 비용을 확인합니다

        

          예상 행 수, 예상 비용, 그리고 구체적 조언 —
          "패턴에 연결되지 않은 노드가 있습니다. 관계로 연결하지 않으면 카티션 곱이 됩니다."
          에이전트가 자기 나쁜 질의를 스스로 철회하게 두는 편이 나중에 죽이는 것보다 낫습니다.
        

      

      

        og_explain_error(graph, query)
        
오류가 정정을 들고 옵니다

        

          code는 릴리스 간 안정적이라 재시도 로직이 분기할 수 있습니다.
          후보는 실제 카탈로그에 대한 편집 거리에서 나옵니다 — 모델이 뭐가 있는지 추측할 필요가 없습니다.
        

        
{"code":"UNKNOWN_LABEL",
 "message":"unknown label 'Persn' …
            did you mean: Person",
 "suggestions":["Person"]}

      

      

        og_diagnose_empty(graph, query)
        
빈 결과가 가장 어렵습니다

        

          틀린 게 없고, 읽을 것도 없으니까요. 그래서 패턴을 원소 단위로 걸으며
          어디서 0행이 되었는지를 보고합니다 — "패턴은 매칭됐고, WHERE 절이 모든 행을 지웠습니다."
        

      

      

        og_create_role / og_apply_role
        
할 수 있는 일을 제한합니다

        

          역할별 statement_timeout, work_mem,
          읽기 전용, 행 수 상한. 모든 og_cypher 호출은
          주체·질의문·행 수·소요 시간·오류 코드와 함께 og_audit에 남습니다 —
          사전 예방만이 아니라 사후 검토가 가능합니다.
        

      

      

        og_set_source / og_history / og_as_of
        
답에 출처를 답니다

        

          출처 URL·신뢰도·작성자를 노드에 붙이고, 필요한 타입만 이력 추적을 켭니다(쓰기 비용이 있으니 기본은 꺼짐).
          og_as_of는 이력이 없으면 현재 값을 돌려주는 대신 오류를 냅니다 —
          시제 질문에 현재형 데이터로 조용히 답하는 건 지식베이스의 신뢰를 무너뜨리는 종류의 오답이기 때문입니다.
        

      

    

  







  

    

      
05 · 활용 용도

      

        
이미 PostgreSQL을 쓰고 있는데 그래프가 필요해진 순간

        
각 항목에 실제 호출할 함수까지 적었습니다. 데모가 아니라 오늘 쓸 수 있는 표면입니다.

      

    


    

      

        GraphRAG · 에이전트 지식베이스
        
LLM이 질의하고, 스스로 고치고, 출처를 다는 지식 그래프

        

          벡터 검색만으로는 "왜 이 문서인가"를 설명하지 못하고, 그래프만으로는 의미 유사도를 못 잡습니다.
          여기서는 둘이 같은 릴레이션에 있어서 og_hybrid_search()가
          벡터 순위와 그래프 근접도를 RRF로 융합하고 두 성분 점수를 함께 돌려줍니다.
        

        
og_schema_for → og_estimate → og_cypher
→ og_explain_error / og_diagnose_empty → 재시도
og_hybrid_search(graph, type, prop, q, anchor, k)

      


      

        전사 온톨로지 · 마스터 데이터
        
도메인 모델을 문서가 아니라 데이터베이스가 강제합니다

        

          다중 상속 타입 계층, 역할별 참여자 타입 제약, 카디널리티, transitive·
          symmetric 규칙. 상위 개념 하나로 질의하면 모든 하위 개념이 답하므로,
          개념 체계가 바뀌어도 애플리케이션 질의를 다시 쓰지 않습니다.
        

        
og_create_type(g,'EV','entity',ARRAY['Car'])
og_add_role(g,'OWNS','owner','Person',0)
og_add_rule(g,'PART_OF','transitive')

      


      

        Supabase · PostgREST 제품
        
추가 서비스 0개로 제품에 그래프 기능을 붙입니다

        

          og_cypher_json()을 PostgREST RPC로 노출하면 supabase-js가 바로 호출합니다.
          결과는 jsonb라 어떤 드라이버든 특수 라이브러리 없이 읽습니다.
          그리고 RLS가 순회 도중 적용되므로 멀티테넌시 격리를 애플리케이션 코드로 다시 구현하지 않습니다.
        

        
og_map_table(g, 'public.users', 'User', 'id', '{...}')
  — 기존 테이블을 복사 없이 노드 타입으로
og_enable_rls(g, 'User', 'tenant_id = current_tenant()')

      


      

        의미 검색 · 추천
        
"이것과 비슷한 관계를 찾아줘"

        

          노드 유사도는 어디에나 있습니다. 여기서는 관계 자체가 임베딩을 갖습니다 —
          "이 협업과 비슷한 협업", "이 인용 맥락과 비슷한 인용". 엣지 타입 테이블의 HNSW 인덱스이므로
          그래프 술어가 사후 필터가 아니라 인덱스와 같은 스캔에서 걸립니다.
        

        
og_similar('default', <edge_id>, 'context', 3)
og_vector_search(g, t, p, q, k, filter := 'p_year > 2020')
og_stale_embeddings(g) — 원본이 바뀐 임베딩 추적

      


      

        시맨틱 웹 자산 이관
        
OWL 온톨로지를 타입 계층으로 그대로 받습니다

        

          Turtle / N-Triples를 적재하면 OWL 클래스는 타입으로, rdfs:subClassOf는
          상속으로, domain/range는 역할로 매핑됩니다. 다시 직렬화할 때는 매핑되지 않은 트리플까지 보존합니다.
          매핑되지 않은 것과 그 이유는 og_mapping_report()가 알려줍니다 — 조용히 삼키지 않습니다.
        

        

          주의: 이 영역은 부분 구현입니다. RDF 적재·덤프와 OWL 매핑은 동작하지만, SPARQL은 아직입니다.
        

        
og_load_rdf(g, document, 'turtle')
og_dump_rdf(g, 'turtle') · og_mapping_report(g)

      


      

        규제 · 감사 · 데이터 거버넌스
        
답이 어디서 왔고 언제 그랬는지 말할 수 있어야 하는 도메인

        

          모든 og_cypher 호출의 감사 로그, 엔터티별 출처·신뢰도·작성자,
          선택적 변경 이력, 과거 시점 조회. 그리고 이력이 없으면 추정하지 않고 오류를 냅니다.
          역할별 자원 상한으로 폭주 질의도 사전에 막습니다.
        

        
og_set_source(id, 'https://…/doc/42', 0.92, 'ingest-v3')
og_enable_history(g,'Person') · og_as_of(id, ts)
og_data.og_audit — principal · query · rows · ms · code

      

    


    


    

      이럴 땐 쓰지 마십시오
      
맞지 않는 경우도 먼저 말씀드립니다

      
    
        
  • 1~2홉 고정 깊이 조회만 필요하다면 — 인덱스 두 개짜리 재귀 CTE가 더 빠릅니다. 위 벤치마크가 그렇게 말합니다. 타입 시스템·Cypher·벡터가 필요 없다면 그걸 쓰십시오.
    • 
        
  • WITH·UNION에 의존하는 질의가 많다면 — 아직 컴파일되지 않습니다. 조용히 다르게 해석하지 않고 대안을 제시하며 명확히 실패합니다. 질의를 쪼개거나 og_cypher_sql() 출력을 SQL CTE로 감싸는 우회가 필요합니다.
    • 
        
  • 분산 쓰기 · 샤딩이 지금 필요하다면 — 읽기 복제본은 오늘 동작하지만 샤딩은 설계만 되어 있습니다. 2단계 커밋 없는 분산 쓰기는 헌법 원칙을 조용히 위반하는 일이라 미뤘습니다. 식별자에 shard 비트는 이미 예약되어 있어 나중에 재작성 없이 분산됩니다.
    • 
        
  • PostgreSQL을 쓰지 않기로 이미 결정했다면 — 이 제품의 장점 절반은 "확장이라서 공짜로 따라오는 것들"입니다. 그 전제가 없으면 절반이 사라집니다.

06 · Neo4j 샘플 이식

      

        
Neo4j 애플리케이션이 접속 URI만 바꾸면 그대로 돕니다.

        

          :play movies 뒤에 있는 그 예제 —
          neo4j-graph-examples/movies 의
          데이터셋과 공식 가이드 쿼리, 그리고 공식 샘플 앱입니다. 한 줄도 이 데이터베이스에
          맞게 고쳐 쓰지 않았습니다. 고쳐 쓰면 다른 질문에 답하는 셈이기 때문입니다.
        

      

    


    

      

        프로토콜 · Bolt 게이트웨이
        
드라이버도, 세션도, 결과 객체도 그대로입니다

        

          Neo4j 드라이버가 Bolt로 붙습니다(명세 011). 게이트웨이는 파서도 플래너도
          캐시도 사용자 저장소도 갖지 않습니다 — 받은 Cypher를 og_cypher()로
          넘길 뿐이라 질의 경로는 여전히 하나입니다. 인증은 PostgreSQL 역할 그대로여서
          권한·RLS·감사가 둘로 갈라지지 않고, 세션의 database는
          그래프가 됩니다. PostgreSQL 프로토콜 경로는 아무것도 달라지지 않습니다.
        

        
# Neo4j
GraphDatabase.driver("bolt://neo4j:7687",
                    auth=basic_auth(user, pw))

# Ontological — 바뀌는 건 이 두 줄뿐
GraphDatabase.driver("bolt://og:7687",
                    auth=basic_auth(pg_role, pg_pw))

        이 실행이 잡아낸 것
        
샘플을 그대로 돌리지 않았다면 못 봤을 다섯 가지

        

          공식 샘플은 우리가 쓰지 않는 방식으로 Cypher를 씁니다. 그래서 회귀 스위트가 통과하는 동안에도
          아래가 살아 있었고, 이 실행에서 드러나 고쳐졌습니다.
        

        
1. 리스트 리터럴이 타입 없이 to_jsonb()로 → 컴파일 실패
   ['Neo'] 같은 배열 프로퍼티가 있는 MERGE 전부

2. 리스트 ↔ 배열 컬럼 비교가 text[] = jsonb
   → 배열 컬럼이 힌트면 ARRAY[...]::text[] 로 컴파일

3. MERGE가 이미 바인딩된 끝점을 무시
   MERGE (a)-[:DIRECTED]->(m) 이 그래프의 아무 DIRECTED나
   찾아서 두 번째 간선을 만들지 않음 → 44개가 1개로

4. 관계 유일성(isomorphism) 미적용
   (a)-[:ACTED_IN]->(m)<-[:ACTED_IN]-(b) 에서 a가
   자기 자신의 공동출연자로 → 51행(정답 39행)

5. 트랜잭션 안의 RUN 은 db 를 다시 보내지 않는다
   → 게이트웨이가 기본 그래프로 되돌려 커밋이 엉뚱한
     그래프로. 드라이버가 아니었으면 못 봤을 버그

      

      

        직접 재현하기

          어느 포트가 Bolt를 말하는지는 주장하지 않고 실제 핸드셰이크로 확인합니다.

이 릴리스는 Table Access Method가 아닙니다

        

          AM을 구현한다는 건 튜플 직렬화, 가시성, vacuum, WAL 리소스 매니저를 직접 쓴다는 뜻입니다.
          인접 세그먼트와 타입 컬럼이 이미 성능 의도를 담고 있으므로 AM은 v2 항목이고,
          og_expand()가 그 변경을 넘어 살아남을 안정적 인터페이스입니다.

          그리고 plan.md에 그렇게 적혀 있습니다. 실제로 중요한 부분인 옵티마이저 통합은 진짜입니다.
        

      

    

  







  

    

      
08 · 시작하기

      

        
Docker 하나면 전부 들어 있습니다

        
엔진, PostgreSQL 16, pgvector, 데모 데이터셋, 그리고 Studio까지.

      

    


    

      

        1 · 설치
        
# 컨테이너 빌드 후 확장 설치 + 데모 데이터
docker build -f docker/Dockerfile.dev -t ontological-dev .
docker run -d --name og -v "$PWD":/work \
  -p 28816:28816 -w /work ontological-dev sleep infinity

cargo pgrx install --features pg16
psql -c "CREATE EXTENSION ontological CASCADE"
psql -f examples/demo.sql

# Neo4j Browser 스타일 콘솔
cd portal && npm install
PGHOST=127.0.0.1 PGPORT=28816 \
PGDATABASE=og PGUSER=dev npm start

# → http://localhost:7474
