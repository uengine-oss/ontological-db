# Feature Specification: 네이티브 사이퍼 질의 엔진 (Native Cypher Query Engine)

**Feature Branch**: `003-cypher-query-engine`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "사이퍼 쿼리를 기본적으로 지원해야 하고, 사이퍼가 중심이 되는 그래프 DB"

## 개요

Apache AGE는 Cypher를 `cypher('graph', $$ MATCH ... $$)` 형태의 함수 인자 문자열로 받는다.
그 결과 PostgreSQL 옵티마이저는 그래프 패턴 내부를 전혀 볼 수 없고, 파라미터 바인딩·plan
cache·통계 기반 조인 순서 결정이 모두 무력화된다.

이 스펙은 Cypher를 **PostgreSQL이 이해하는 1급 질의 언어**로 만든다: 자체 파서가 AST를 만들고,
논리 계획으로 정규화한 뒤, 저장 엔진(001)의 접근 경로와 타입 시스템(002)의 상속 인덱스를
활용하는 물리 계획으로 내려간다. 실행은 PostgreSQL Custom Scan 프레임워크 위에서 이루어져
`EXPLAIN`, 커서, 병렬 질의, 트랜잭션이 그대로 적용된다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 표준 Cypher가 그대로 동작한다 (Priority: P1)

Neo4j 경험이 있는 개발자가 기존 Cypher 질의를 거의 수정 없이 실행한다. `MATCH`, `WHERE`,
`RETURN`, `CREATE`, `MERGE`, `SET`, `DELETE`, `WITH`, `ORDER BY`, `SKIP`/`LIMIT`,
집계, 가변 길이 경로가 기대대로 동작한다.

**Why this priority**: Cypher 호환성이 없으면 이 제품을 쓸 이유가 없다.

**Independent Test**: openCypher TCK 스위트를 실행하여 통과율을 측정한다.

**Acceptance Scenarios**:

1. **Given** 표준 openCypher 읽기 질의가 주어지면, **When** 실행하면, **Then** Neo4j와
   동일한 결과 집합(순서 무관 비교)을 반환한다.
2. **Given** `CREATE`/`MERGE`/`SET`/`DELETE` 를 포함한 쓰기 질의가 주어지면, **When**
   실행하면, **Then** 그래프 상태가 openCypher 의미론대로 변경되고 트랜잭션에 참여한다.
3. **Given** 가변 길이 경로 패턴 `-[:KNOWS*1..3]->` 이 주어지면, **When** 실행하면,
   **Then** 중복 관계 없는 경로(trail semantics)가 openCypher 규칙대로 반환된다.
4. **Given** 지원하지 않는 구문이 주어지면, **When** 실행하면, **Then** 어느 구문이 미지원
   인지와 대안을 명시한 오류가 반환된다(조용한 오동작 금지).

---

### User Story 2 - 옵티마이저가 그래프 패턴을 이해한다 (Priority: P1)

성능 엔지니어가 여러 홉과 필터가 섞인 질의를 `EXPLAIN` 으로 확인한다. 옵티마이저는 선택도가
가장 높은 지점에서 패턴 매칭을 시작하고, 확장 순서와 조인 방식을 통계 기반으로 결정한다.

**Why this priority**: 옵티마이저가 그래프를 못 보면 001의 저장 성능이 낭비된다. AGE와의
근본적 차별점이다.

**Independent Test**: 여러 시작점이 가능한 패턴을 두고, 데이터 분포를 바꿔가며 선택된 실행
계획이 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `MATCH (a:Person {email:$e})-[:WORKS_AT]->(c:Company)` 처럼 한쪽이 매우
   선택적인 패턴에서, **When** 계획을 확인하면, **Then** 선택적인 쪽에서 시작해 확장하는
   계획이 선택된다.
2. **Given** 동일 질의 형태에서 데이터 분포만 반대로 바꾸면, **When** 통계 갱신 후 계획을
   확인하면, **Then** 시작점이 반대로 바뀐다.
3. **Given** 다중 홉 패턴에서, **When** `EXPLAIN (ANALYZE)` 를 실행하면, **Then** 각 그래프
   연산자의 예상/실제 행수, 소요 시간, 버퍼 사용량이 표시된다.
4. **Given** 관계 타입과 방향이 지정된 패턴에서, **When** 계획을 확인하면, **Then** 저장
   엔진의 타입·방향별 인접 접근 경로가 선택된다.
5. **Given** 상위 타입 레이블을 사용한 패턴에서, **When** 계획을 확인하면, **Then** 상속
   인덱스 기반 범위 조건이 계획에 나타나고 재귀 노드가 없다.

### User Story 3 - Cypher와 SQL이 한 문장에서 섞인다 (Priority: P1)

애플리케이션 개발자가 기존 관계형 테이블(주문, 결제)과 그래프(고객 관계망)를 하나의 질의로
조인한다. 결과는 일반 SQL 결과 집합이며 기존 드라이버로 그대로 읽힌다.

**Why this priority**: PostgreSQL 위에 있는 이유 자체다. 이 상호운용이 없으면 별도 그래프
DB를 쓰는 것과 다르지 않다.

**Independent Test**: 그래프 결과와 일반 테이블을 조인하는 질의를 표준 PostgreSQL 드라이버로
실행하고, 결과 타입과 조인 계획을 검증한다.

**Acceptance Scenarios**:

1. **Given** 그래프 패턴 결과와 일반 테이블이 있을 때, **When** 두 결과를 `JOIN` 하면,
   **Then** 표준 SQL 조인으로 처리되고 결과 컬럼이 일반 PostgreSQL 타입으로 반환된다.
2. **Given** Cypher 표현식에서 값을 반환할 때, **When** 클라이언트가 결과를 읽으면,
   **Then** `agtype` 같은 불투명 타입이 아니라 표준 타입(또는 문서화된 컴포지트)으로
   해석 가능하다.
3. **Given** SQL의 `WHERE` 절 조건이 그래프 패턴의 결과를 제한할 때, **When** 계획을 보면,
   **Then** 가능한 조건이 그래프 연산자 안으로 push-down 된다.
4. **Given** 그래프 질의가 SQL 서브쿼리 안에 있을 때, **When** 실행하면, **Then** 동일
   트랜잭션·동일 스냅샷에서 동작한다.

---

### User Story 4 - 파라미터화된 질의가 계획을 재사용한다 (Priority: P1)

서비스가 초당 수천 건의 동일 형태 질의를 파라미터만 바꿔 실행한다. 매번 파싱·계획하지 않고
준비된 계획을 재사용한다.

**Why this priority**: AGE의 문자열 인자 방식이 구조적으로 못 하는 것이며, 실서비스 처리량을
좌우한다.

**Independent Test**: 동일 질의를 파라미터를 바꿔 반복 실행하고 파싱/계획 시간이 첫 실행 이후
사라지는지 측정한다.

**Acceptance Scenarios**:

1. **Given** 파라미터를 포함한 Cypher 질의가 prepared statement로 준비되면, **When** 파라미터를
   바꿔 반복 실행하면, **Then** 파싱·계획이 재수행되지 않는다.
2. **Given** 파라미터 값이 문자열일 때, **When** 그 안에 Cypher 구문이 포함되어 있으면,
   **Then** 값으로만 취급되어 주입(injection)이 발생하지 않는다.
3. **Given** 파라미터 값의 분포가 극단적으로 다를 때, **When** 반복 실행하면, **Then** 계획
   재사용과 재계획 사이를 선택하는 정책이 적용되고 그 동작이 관찰 가능하다.

---

### User Story 5 - 질의가 예측 가능하게 제어된다 (Priority: P2)

운영자가 폭주하는 질의를 제한한다. 타임아웃, 메모리 상한, 방문 노드 수 상한을 걸고, 초과 시
명확한 오류를 받는다. 실행 중인 질의를 취소할 수 있다.

**Why this priority**: 그래프 질의는 실수 하나로 조합 폭발을 일으킨다. 특히 LLM이 질의를
생성하는 환경(008)에서는 필수 안전장치다.

**Independent Test**: 의도적으로 폭발하는 패턴을 실행하고 각 상한이 작동하는지, 취소가 즉시
반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 데카르트 곱을 만드는 패턴이 실행되면, **When** 계획 단계에서 감지되면, **Then**
   경고가 발생하고(설정에 따라) 실행이 거부된다.
2. **Given** 질의 타임아웃이 설정되어 있고, **When** 초과하면, **Then** 질의가 중단되고
   부분 결과가 커밋되지 않으며 어떤 상한을 넘었는지 오류에 표시된다.
3. **Given** 장시간 실행 중인 질의가 있을 때, **When** `pg_cancel_backend` 를 호출하면,
   **Then** 수 초 이내에 취소된다.
4. **Given** 방문 노드 수 상한이 설정되어 있고, **When** 트래버설이 초과하면, **Then**
   초과 시점의 진행 상황을 포함한 오류가 반환된다.

---

### User Story 6 - 무거운 질의가 병렬로 처리된다 (Priority: P3)

분석가가 전체 그래프를 훑는 집계 질의를 실행한다. 여러 워커가 나누어 처리한다.

**Why this priority**: 분석 워크로드의 처리량을 좌우하지만, 단일 스레드 정확성이 먼저다.

**Independent Test**: 대형 집계 질의에서 워커 수를 늘려가며 확장성을 측정한다.

**Acceptance Scenarios**:

1. **Given** 전체 타입 스캔을 포함한 집계 질의에서, **When** 병렬 워커가 활성화되면,
   **Then** 워커 수에 대해 확장되며 결과는 직렬 실행과 동일하다.
2. **Given** 병렬 실행 중 한 워커에서 오류가 발생하면, **When** 질의가 종료되면, **Then**
   전체 질의가 실패하고 부분 결과가 반환되지 않는다.

---

### Edge Cases

- **조합 폭발**: 필터 없는 다중 홉 패턴이 중간 결과를 폭증시킬 때 — 계획 단계 경고와 실행 중
  상한이 함께 작동해야 한다.
- **순환 경로**: 사이클이 있는 그래프에서 가변 길이 경로가 무한 확장되지 않아야 한다
  (trail semantics + 깊이 상한).
- **빈 패턴 / OPTIONAL MATCH**: 매칭이 없을 때 `OPTIONAL MATCH` 의 null 전파가 openCypher
  의미론을 정확히 따라야 한다.
- **NULL 의미론**: 세 값 논리(true/false/null)가 SQL이 아닌 Cypher 규칙을 따라야 한다.
- **동일 변수 재사용**: 같은 관계 변수가 한 패턴에서 두 번 나타날 때의 의미론.
- **대소문자/이스케이프**: 백틱으로 감싼 레이블·프로퍼티 이름, 유니코드 식별자 처리.
- **MERGE 경합**: 두 트랜잭션이 같은 패턴을 동시에 `MERGE` 할 때 중복 생성이 없어야 한다.
- **큰 결과 집합**: 수백만 행 결과를 커서로 스트리밍할 때 메모리가 결과 크기에 비례해 증가하지
  않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

**언어 지원**

- **FR-001**: 시스템은 openCypher 문법을 파싱하는 자체 파서를 제공해야 하며, Cypher를 문자열
  인자로 받는 함수 인터페이스에 의존해서는 안 된다.
- **FR-002**: 시스템은 읽기 절(`MATCH`, `OPTIONAL MATCH`, `WHERE`, `WITH`, `RETURN`,
  `ORDER BY`, `SKIP`, `LIMIT`, `UNION`, `UNWIND`)을 지원해야 한다.
- **FR-003**: 시스템은 쓰기 절(`CREATE`, `MERGE`, `SET`, `REMOVE`, `DELETE`,
  `DETACH DELETE`)을 지원해야 한다.
- **FR-004**: 시스템은 가변 길이 경로 패턴과 최단 경로 함수를 지원해야 한다.
- **FR-005**: 시스템은 집계 함수, 리스트/맵 표현식, 경로 함수, 문자열/수학/시간 함수 등
  openCypher 표준 함수 라이브러리를 지원해야 한다.
- **FR-006**: 시스템은 openCypher NULL 의미론과 타입 강제 규칙을 정확히 구현해야 한다.
- **FR-006a**: 시스템은 openCypher 관계 유일성(isomorphism)을 구현해야 한다. 하나의 `MATCH`
  절은 같은 관계를 두 번 순회해서는 안 되며, 이 규칙의 범위는 절 단위다.
- **FR-007**: 시스템은 타입 시스템(002)의 상속·role·제약을 표현하는 Cypher 확장 DDL 구문을
  제공해야 한다.
- **FR-008**: 미지원 구문에 대해 시스템은 파싱 단계에서 명확한 오류를 반환해야 하며, 의미를
  임의로 변경해 실행해서는 안 된다.
- **FR-009**: 시스템은 지원 구문 매트릭스를 문서와 introspection API로 제공해야 한다.

**계획 수립**

- **FR-010**: 시스템은 Cypher AST를 논리 계획으로 변환하고, 술어 push-down, 프로젝션 가지치기,
  패턴 재정렬을 포함한 규칙 기반 최적화를 수행해야 한다.
- **FR-011**: 시스템은 저장 엔진(001)이 제공하는 통계를 사용해 비용 기반으로 패턴 매칭 시작점,
  확장 순서, 조인 방식을 결정해야 한다.
- **FR-012**: 시스템은 상위 타입 레이블 조건을 타입 시스템(002)의 상속 인덱스 범위 조건으로
  변환해야 하며, 재귀 실행 노드를 생성해서는 안 된다.
- **FR-013**: 시스템은 관계 타입·방향 조건을 저장 엔진의 타입·방향별 인접 접근 경로로 매핑해야
  한다.
- **FR-014**: 시스템은 프로퍼티 조건을 가능한 경우 인덱스 스캔 또는 저장 엔진 필터로
  push-down 해야 한다.
- **FR-015**: 시스템은 데카르트 곱과 무제한 확장을 계획 단계에서 감지하고 경고해야 한다.
- **FR-016**: 시스템은 계획을 캐시하고 파라미터 재바인딩 시 재사용해야 한다.

**실행**

- **FR-017**: 그래프 연산자는 PostgreSQL Custom Scan/Join 프레임워크 위에서 실행되어야 하며,
  `EXPLAIN`, `EXPLAIN ANALYZE`, 커서, 트랜잭션과 통합되어야 한다.
- **FR-018**: 실행은 스트리밍(pull) 모델이어야 하며, 중간 결과 전체를 메모리에 적재해서는
  안 된다. 메모리를 초과하는 연산(정렬, 해시 조인)은 디스크 스필을 지원해야 한다.
- **FR-019**: 시스템은 질의 취소 요청에 응답해야 하며, 그래프 연산자 내부에도 취소 확인 지점이
  있어야 한다.
- **FR-020**: 시스템은 질의 단위 리소스 상한(실행 시간, 메모리, 방문 노드/엣지 수, 결과 행 수)을
  설정하고 강제해야 한다.
- **FR-021**: 상한 초과 시 오류는 어떤 상한을 초과했는지와 초과 시점 진행 상황을 포함해야 한다.
- **FR-022**: 시스템은 전체 스캔 계열 그래프 연산자에 대해 병렬 실행을 지원해야 한다.
- **FR-023**: 쓰기 질의는 PostgreSQL 트랜잭션 의미론을 따라야 하며, 동시 `MERGE` 가 중복
  엔티티를 생성해서는 안 된다.

**인터페이스**

- **FR-024**: Cypher 질의는 표준 PostgreSQL 프로토콜(psql, JDBC, psycopg 등 기존 드라이버)로
  실행 가능해야 하며, 전용 클라이언트를 요구해서는 안 된다.
- **FR-024a**: Bolt(Neo4j 와이어 프로토콜)는 본 스펙의 **범위 밖**이며, 스펙
  **011-bolt-protocol-gateway** 가 코어 밖의 게이트웨이로 제공한다. 본 스펙이 지키는 것은
  "질의 경로는 `og_cypher()` 하나"라는 성질이다 — 게이트웨이는 전송 계층일 뿐 두 번째
  Cypher 구현이 아니며, 인증·권한·감사도 PostgreSQL 것 하나를 그대로 쓴다.
  두 경로의 결과 동등성은 `tests/neo4j-movies/` 가 공식 Movie Graph 샘플로 검증한다.
- **FR-025**: Cypher 결과는 표준 PostgreSQL 타입 또는 문서화된 컴포지트 타입으로 반환되어야
  하며, 클라이언트가 별도 파서를 요구하는 불투명 타입이어서는 안 된다.
- **FR-026**: 시스템은 파라미터 바인딩을 지원해야 하며, 파라미터 값이 질의 구조를 변경할 수
  없어야 한다(주입 방지).
- **FR-027**: 시스템은 Cypher 질의 결과를 SQL에서 테이블처럼 참조하고 조인할 수 있게 해야 한다.
- **FR-028**: 시스템은 질의 실행 통계(계획, 실행 시간, 방문 노드/엣지 수, 캐시 적중)를
  조회 가능한 형태로 기록해야 한다.

### Key Entities

- **Cypher AST**: 파싱된 질의의 구문 트리.
- **Logical Plan**: 관계대수 + 그래프 연산자(패턴 매칭, 확장, 경로)로 구성된 최적화 대상 표현.
- **Physical Plan**: PostgreSQL Custom Scan 노드로 구성된 실행 가능 계획.
- **Graph Operators**: `NodeScan(type)`, `Expand(type, direction)`, `VarLengthExpand`,
  `PathBuild`, `PatternJoin` 등 그래프 전용 실행 연산자.
- **Plan Cache Entry**: 질의 형태 → 준비된 계획 매핑. 파라미터 분포 정보를 동반한다.
- **Query Budget**: 질의 단위 리소스 상한 집합.
- **Query Statistics**: 실행 후 남는 계획·비용·실제 지표 기록.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: openCypher TCK 통과율이 초기 릴리스에서 **85% 이상**이며, 이후 릴리스에서 절대
  회귀하지 않는다.
- **SC-002**: LDBC SNB Interactive 질의 집합에서 Apache AGE 대비 기하평균 지연시간이
  **10배 이상** 개선된다.
- **SC-003**: 파라미터화된 질의의 2회차 이후 실행에서 파싱·계획 오버헤드가 전체 지연시간의
  **1% 미만**이다.
- **SC-004**: 시작점 선택이 중요한 벤치마크 질의 집합에서, 옵티마이저가 선택한 계획이 최적
  계획 대비 **2배 이내** 지연시간을 갖는 비율이 **90% 이상**이다.
- **SC-005**: 데이터 분포를 반전시켰을 때 계획이 실제로 바뀌는 비율이 대상 질의 집합의
  **80% 이상**이다.
- **SC-006**: 500만 행 결과를 커서로 스트리밍할 때 서버 메모리 사용량이 **결과 크기와 무관하게
  상수**에 수렴한다.
- **SC-007**: 실행 중인 질의의 취소가 **3초 이내** 반영된다.
- **SC-008**: 파라미터를 통한 질의 주입 시도가 보안 테스트 스위트에서 **0건** 성공한다.
- **SC-009**: 전체 스캔 집계 질의가 워커 8개에서 단일 워커 대비 **5배 이상** 빠르다.
- **SC-010**: 기존 PostgreSQL 드라이버(psql, JDBC, psycopg3) 3종 모두에서 별도 라이브러리
  없이 Cypher 질의 실행과 결과 해석이 가능하다.
- **SC-011**: Neo4j 공식 Movie Graph 샘플의 데이터셋 구문과 가이드 Cypher 질의가 **수정 없이**
  실행되며, 같은 데이터를 적재한 Neo4j와 **전 질의에서 동일한 결과 행 수**를 낸다.
  타입 선언(002)과 그로 인해 불필요해진 `CREATE CONSTRAINT` 만이 허용되는 차이다.
  같은 질의를 스펙 011의 Bolt 경로로 보내도 결과는 동일해야 한다 — 전송 계층이 의미론을
  바꾸지 않는다는 것이 두 경로를 두는 전제다.

## Assumptions

- 접근 경로, 통계, 비용 추정치는 스펙 **001-graph-storage-engine**이 제공한다.
- 타입 이름 해석, 상속 범위 조건, 제약 검증은 스펙 **002-ontology-type-system**이 제공한다.
- 벡터 검색 연산자와 하이브리드 계획 통합은 스펙 **004-vector-hybrid-search**에서 본 엔진의
  연산자로 추가된다.
- SQL 임베딩 문법의 세부(함수형 vs `GRAPH_TABLE` 스타일)는 스펙 **005-postgres-supabase-interop**
  에서 확정한다. 본 스펙은 "SQL에서 조인 가능해야 한다"는 요구만 규정한다.
- 분산 실행(원격 노드로의 연산 push-down)은 스펙 **007-distributed-cluster** 범위이며, 본
  스펙의 계획 표현은 분산 계획으로 확장 가능한 형태여야 한다.
- SPARQL/GraphQL은 스펙 **006** 에서 본 논리 계획으로 컴파일된다. 따라서 논리 계획은 Cypher
  전용 구조가 아니라 언어 중립적이어야 한다.
- openCypher TCK를 정확성 기준선으로 사용하며, Neo4j 고유 확장(APOC 등)은 초기 범위 밖이다.
- 목표 문법 기준은 openCypher이며 ISO GQL 정렬은 로드맵 항목이다.
