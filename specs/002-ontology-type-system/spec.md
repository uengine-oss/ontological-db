# Feature Specification: 온톨로지 타입 시스템과 상속 인덱싱 (Ontology Type System & Inheritance Indexing)

**Feature Branch**: `002-ontology-type-system`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "Neo4j는 멀티레이블을 지원하지만 상속이 약하다. TypeDB를 벤치마킹해 상속 구조와 인덱스 구조를 참고하여 상속 관계를 한 번에 찾아낼 수 있는 구조가 필요하다"

## 개요

Neo4j의 레이블은 문자열 태그다. `:Car` 를 붙인 노드는 `:Vehicle` 질의에 잡히지 않으며,
사용자가 두 레이블을 모두 붙여 관리해야 한다. 계층이 깊어지면 관리 비용과 오류가 폭증한다.

TypeDB는 entity/relation/attribute 타입과 서브타입 계층, role 개념을 1급으로 갖는다. 대신
PostgreSQL 생태계 밖에 있다.

이 스펙은 **TypeDB 수준의 개념 모델을 PostgreSQL 카탈로그 위에 구현**하고, 핵심적으로
**상속 판정을 재귀 없이 단일 범위 비교로 수행하는 인덱스 구조**를 정의한다. 이것이
`MATCH (v:Vehicle)` 이 수백만 개의 `Car`, `Truck`, `EV` 를 상수 시간 판정으로 걸러내는
근거이며, 헌법 원칙 IV의 실현이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 상위 타입으로 물으면 모든 하위 타입이 잡힌다 (Priority: P1)

모델러가 `Vehicle` 하위에 `Car`, `Truck`, `Motorcycle` 을, `Car` 하위에 `EV`, `ICE` 를
정의한다. 애플리케이션은 `MATCH (v:Vehicle)` 만 쓰면 되고, 새 하위 타입이 추가되어도 질의를
고치지 않는다.

**Why this priority**: 이 스펙의 존재 이유이자 Neo4j 대비 핵심 차별점이다.

**Independent Test**: 5단계 깊이·1,000개 타입의 계층을 만들고 최상위 타입 질의가 모든 후손
인스턴스를 반환하는지, 그리고 그 판정에 재귀 실행 계획이 없는지 `EXPLAIN` 으로 검증한다.

**Acceptance Scenarios**:

1. **Given** `EV ⊂ Car ⊂ Vehicle` 계층과 각 타입의 인스턴스가 있고, **When**
   `MATCH (v:Vehicle) RETURN count(v)` 를 실행하면, **Then** 세 타입 인스턴스가 모두
   집계된다.
2. **Given** 동일 계층에서, **When** 실행 계획을 확인하면, **Then** 계층을 펼치기 위한 재귀
   CTE나 반복 카탈로그 조회가 계획에 존재하지 않는다.
3. **Given** 1,000개 타입·깊이 8의 계층에서, **When** 최상위 타입으로 질의하면, **Then**
   타입 판정 비용이 계층 깊이·후손 수와 무관하게 일정하다.
4. **Given** 기존 계층에 새 하위 타입 `Hybrid ⊂ Car` 를 추가하면, **When** 기존
   `MATCH (v:Vehicle)` 질의를 재실행하면, **Then** 질의 수정 없이 `Hybrid` 인스턴스가
   포함된다.

### User Story 2 - 관계에도 타입과 역할(role)이 있다 (Priority: P1)

모델러가 `Employment` 관계 타입을 정의하고 `employer`, `employee` 두 role을 선언한다.
각 role이 받을 수 있는 타입을 제약하고, `Contract ⊂ Employment` 같은 관계 상속도 정의한다.

**Why this priority**: 관계를 단순 문자열 타입으로만 두면 온톨로지가 성립하지 않는다. role은
n-ary 관계와 제약 검증의 기반이다.

**Independent Test**: role 제약을 위반하는 엣지 생성이 거부되는지, 상위 관계 타입으로 질의할
때 하위 관계가 반환되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** `Employment` 이 `employer: Organization`, `employee: Person` role을 갖고,
   **When** `employer` 자리에 `Person` 을 넣어 엣지를 만들면, **Then** 제약 위반으로 거부되고
   위반한 role과 기대 타입을 담은 오류가 반환된다.
2. **Given** `Contract ⊂ Employment` 이고 `Contract` 엣지들이 존재할 때, **When**
   `Employment` 관계로 질의하면, **Then** `Contract` 엣지가 결과에 포함된다.
3. **Given** 3개 이상 role을 갖는 n-ary 관계가 정의되었을 때, **When** 해당 관계를 생성·조회
   하면, **Then** 모든 role player가 보존되고 role 이름으로 접근 가능하다.
4. **Given** 하위 관계 타입이 상위의 role을 더 좁은 타입으로 재정의(role specialization)할 때,
   **When** 엣지를 생성하면, **Then** 좁혀진 제약이 적용된다.

### User Story 3 - 스키마가 데이터 무결성을 지킨다 (Priority: P1)

데이터 스튜어드가 `Person` 은 `email` 을 반드시 하나 가져야 하고, `ssn` 은 유일해야 하며,
`Employment` 의 `employee` role은 정확히 하나여야 한다고 선언한다. 위반하는 쓰기는 거부된다.

**Why this priority**: 에이전트가 쓰는 그래프일수록 스키마 강제가 중요하다. LLM이 만든 잘못된
데이터를 DB가 막아주지 못하면 그래프가 빠르게 오염된다.

**Independent Test**: 각 제약 유형별로 위반 쓰기를 시도하고 거부 여부와 오류 메시지 품질을
검증한다.

**Acceptance Scenarios**:

1. **Given** `Person.email` 이 필수(min 1)로 선언되었고, **When** email 없이 `Person` 을
   생성하면, **Then** 거부되고 누락된 attribute를 명시한 오류가 반환된다.
2. **Given** `Person.ssn` 이 key로 선언되었고 이미 값 `X` 가 존재할 때, **When** 다른
   `Person` 에 같은 `X` 를 부여하면, **Then** 거부된다.
3. **Given** 이미 데이터가 존재하는 타입에 새 필수 제약을 추가할 때, **When** 기존 데이터가
   위반 상태라면, **Then** 스키마 변경이 실패하고 위반 인스턴스 예시가 보고된다.
4. **Given** 제약 위반 쓰기가 트랜잭션 중간에 발생하면, **When** 트랜잭션이 롤백되면,
   **Then** 부분 반영이 남지 않는다.

### User Story 4 - 다중 상속과 다중 타입을 다룬다 (Priority: P2)

모델러가 `Amphibian ⊂ Vehicle, Vessel` 처럼 두 부모를 갖는 타입을 정의한다. 또한 한 노드가
서로 무관한 여러 타입에 동시에 속하는 경우(Neo4j 멀티레이블 마이그레이션)를 지원한다.

**Why this priority**: 현실 온톨로지와 Neo4j 마이그레이션 양쪽에서 필요하지만, 단일 상속
계층이 먼저 동작해야 의미가 있다.

**Independent Test**: 다이아몬드 상속 구조에서 프로퍼티 해석과 상위 타입 질의 결과를 검증한다.

**Acceptance Scenarios**:

1. **Given** `Amphibian ⊂ Vehicle, Vessel` 일 때, **When** `MATCH (x:Vehicle)` 과
   `MATCH (x:Vessel)` 을 각각 실행하면, **Then** 양쪽 모두 `Amphibian` 인스턴스를 포함한다.
2. **Given** 다이아몬드 상속(`D ⊂ B, C`, `B ⊂ A`, `C ⊂ A`)에서 같은 이름의 attribute가
   상속될 때, **When** 타입을 정의하면, **Then** 충돌이 명시적으로 해소되거나(동일 정의면 병합)
   모호하면 정의 시점에 거부된다.
3. **Given** 상속 관계가 없는 타입 `Auditable` 과 `Person` 이 한 노드에 함께 적용될 때,
   **When** 어느 쪽으로 질의해도, **Then** 그 노드가 반환된다.
4. **Given** 타입 정의에 순환(`A ⊂ B`, `B ⊂ A`)이 생기면, **When** 정의를 커밋하면,
   **Then** 순환이 탐지되어 거부된다.

---

### User Story 5 - 스키마가 살아있는 채로 진화한다 (Priority: P2)

운영 중인 그래프에 새 타입을 추가하고, 기존 타입에 attribute를 추가하며, 타입을 계층 중간에
삽입한다. 서비스를 멈추지 않고, 기존 데이터를 재작성하지 않는다.

**Why this priority**: 온톨로지는 반드시 변한다. 스키마 변경이 전체 재적재를 요구하면 실사용이
불가능하다.

**Independent Test**: 대용량 그래프에서 각 스키마 변경 연산의 소요 시간과 질의 차단 여부를
측정한다.

**Acceptance Scenarios**:

1. **Given** 1억 인스턴스를 가진 타입에서, **When** 선택적(optional) attribute를 추가하면,
   **Then** 기존 인스턴스를 재작성하지 않고 즉시 완료된다.
2. **Given** `Car ⊂ Vehicle` 상태에서, **When** 중간 타입 `MotorVehicle` 을 삽입하여
   `Car ⊂ MotorVehicle ⊂ Vehicle` 로 바꾸면, **Then** 기존 `Vehicle` 질의 결과가 변하지 않고
   상속 인덱스가 갱신된다.
3. **Given** 스키마 변경 트랜잭션이 진행 중일 때, **When** 다른 세션이 읽기 질의를 실행하면,
   **Then** 변경 전 스키마로 일관되게 동작하며 차단되지 않는다.
4. **Given** 인스턴스가 존재하는 타입을 삭제하려 하면, **When** 명령을 실행하면, **Then**
   기본적으로 거부되고, 명시적 cascade 옵션이 있을 때만 진행된다.

---

### User Story 6 - 추론된 사실을 질의할 수 있다 (Priority: P3)

모델러가 "`located_in` 은 이행적(transitive)이다", "`spouse` 는 대칭적(symmetric)이다" 같은
규칙을 선언하면, 명시적으로 저장되지 않은 관계도 질의에서 보인다.

**Why this priority**: 온톨로지 DB의 강력한 차별점이지만, 타입 계층과 제약이 먼저 안정화되어야
한다. 006(OWL 어댑터)의 기반이 된다.

**Independent Test**: 이행적 관계 체인을 만들고 직접 저장되지 않은 관계가 질의로 조회되는지,
그리고 결과가 추론된 것임을 식별할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `located_in` 이 이행적이고 `A located_in B`, `B located_in C` 가 저장되어 있을
   때, **When** `A located_in C` 를 질의하면, **Then** 결과가 반환되며 추론된 사실로 표시된다.
2. **Given** 추론 규칙이 활성화된 상태에서, **When** 명시 사실만 필요한 질의를 실행하면,
   **Then** 추론을 끄는 옵션으로 명시 사실만 얻을 수 있다.
3. **Given** 추론이 무한 확장될 수 있는 규칙 조합에서, **When** 질의를 실행하면, **Then**
   깊이/시간 한계가 적용되고 초과 시 명확한 오류가 반환된다.

---

### Edge Cases

- **깊은 계층**: 깊이 50 이상의 타입 계층에서도 상속 판정이 상수 시간이어야 한다.
- **잦은 스키마 변경**: 계층 중간 삽입/삭제가 반복되면 구간 라벨링이 재할당을 요구한다.
  재할당 빈도와 비용이 관리 가능해야 하며(여유 구간 예약), 재할당 중에도 질의가 정확해야 한다.
- **타입 없는 데이터**: 스키마리스로 삽입된 노드는 암묵 타입으로 승격되며, 이후 명시 타입으로
  이관 가능해야 한다.
- **동시 스키마 변경**: 두 세션이 같은 계층을 동시에 수정할 때 직렬화되어야 하며, 한쪽은
  명확한 충돌 오류를 받아야 한다.
- **role 이름 충돌**: 서로 다른 관계 타입이 같은 role 이름을 쓰는 것은 허용되며, 상속 계층
  내에서만 이름이 유일해야 한다.
- **추상 타입**: 인스턴스화할 수 없는 abstract 타입 선언이 가능해야 하고, 직접 인스턴스 생성은
  거부되어야 한다.
- **attribute 타입 변경**: 데이터가 있는 상태에서의 타입 변경은 안전한 확장(int→bigint)만
  허용하고 손실 가능한 변경은 명시적 마이그레이션을 요구해야 한다.

## Requirements *(mandatory)*

### Functional Requirements

**타입 모델**

- **FR-001**: 시스템은 `entity type`, `relation type`, `attribute type` 을 1급 개념으로
  정의·저장해야 한다.
- **FR-002**: 시스템은 세 종류 타입 각각에 대해 서브타입(상속) 관계 선언을 지원해야 한다.
- **FR-003**: 시스템은 다중 상속을 지원해야 하며, 상속 그래프의 순환을 정의 시점에 거부해야
  한다.
- **FR-004**: 시스템은 관계 타입에 이름 있는 role을 선언하고, role별로 허용 타입과
  카디널리티를 제약할 수 있어야 한다.
- **FR-005**: 시스템은 3개 이상 role을 갖는 n-ary 관계를 지원해야 한다.
- **FR-006**: 시스템은 하위 관계 타입이 상속받은 role을 더 좁은 타입으로 재정의(role
  specialization)하는 것을 지원해야 한다.
- **FR-007**: 시스템은 abstract 타입 선언을 지원하며 직접 인스턴스화를 거부해야 한다.
- **FR-008**: 시스템은 하나의 노드가 상속 관계가 없는 복수 타입에 속하는 것을 지원해야 한다
  (Neo4j 멀티레이블 호환).

**상속 인덱싱 (핵심)**

- **FR-009**: 시스템은 타입 계층에 구간 라벨링(interval/nested-set encoding)을 부여하여,
  "타입 X가 타입 Y의 서브타입인가" 판정을 **단일 범위 비교**로 수행해야 한다.
- **FR-010**: 상위 타입 질의의 후손 집합 해석은 **런타임 재귀(CTE, 반복 조회) 없이** 수행되어야
  한다.
- **FR-011**: 상속 판정 비용은 계층 깊이 및 후손 타입 수와 무관해야 한다.
- **FR-012**: 다중 상속으로 단일 구간 라벨링이 불가능한 타입에 대해서는 보조 인코딩(복수 구간
  또는 비트셋)을 유지하되, 판정은 여전히 상수 시간 상한을 가져야 한다.
- **FR-013**: 계층 중간 삽입/삭제 시 라벨 재할당이 필요한 경우, 시스템은 여유 구간을 예약해
  재할당 빈도를 최소화해야 하며, 재할당은 트랜잭션 안에서 원자적으로 수행되어야 한다.
- **FR-014**: 저장 엔진(001)의 타입별 접근 경로는 상속 인덱스를 사용해 대상 타입 집합을
  한 번에 결정해야 한다.

**제약과 무결성**

- **FR-015**: 시스템은 attribute의 필수 여부와 카디널리티(min/max) 제약을 선언·강제해야 한다.
- **FR-016**: 시스템은 key(유일성) 제약을 선언·강제해야 한다.
- **FR-017**: 시스템은 role player의 타입 제약과 role 카디널리티를 강제해야 한다.
- **FR-018**: 제약 위반 시 오류는 위반한 타입·attribute/role·기대값·실제값을 포함해야 하며,
  기계 판독 가능한 오류 코드를 가져야 한다.
- **FR-019**: 시스템은 attribute의 값 도메인(허용 범위, enum, 정규식)을 선언·강제할 수 있어야
  한다.
- **FR-020**: 기존 데이터를 위반하는 제약 추가는 실패해야 하며, 위반 인스턴스 예시를 보고해야
  한다.

**스키마 진화**

- **FR-021**: 스키마 변경은 트랜잭션 안에서 수행되고 롤백 가능해야 한다.
- **FR-022**: 선택적 attribute 추가는 기존 인스턴스를 재작성하지 않고 완료되어야 한다.
- **FR-023**: 계층 중간에 타입을 삽입/제거해도 기존 상위 타입 질의의 의미가 보존되어야 한다.
- **FR-024**: 인스턴스가 존재하는 타입의 삭제는 기본 거부되고, 명시적 cascade 지정 시에만
  허용되어야 한다.
- **FR-025**: 스키마 변경 중에도 동시 읽기 질의는 차단되지 않고 일관된 스키마 스냅샷을 봐야
  한다.
- **FR-026**: 시스템은 스키마 버전을 기록하고 변경 이력을 조회 가능해야 한다.

**추론**

- **FR-027**: 시스템은 관계 특성(이행적, 대칭적, 반사적, 역관계)을 선언하고 질의 시 반영해야
  한다.
- **FR-028**: 추론된 결과는 명시 사실과 구분 가능해야 하며, 추론 근거(어떤 규칙·어떤 사실)를
  조회할 수 있어야 한다.
- **FR-029**: 추론은 질의 단위로 켜고 끌 수 있어야 한다.
- **FR-030**: 추론 확장에는 깊이·시간 한계가 적용되어야 하며, 초과 시 명확한 오류를 반환해야
  한다.

**노출**

- **FR-031**: 전체 타입 카탈로그(계층, role, 제약, 통계)는 SQL과 Cypher 양쪽에서 introspect
  가능해야 한다.
- **FR-032**: 스키마는 텍스트 DDL 형태로 정의·내보내기 가능해야 하며, 내보낸 스키마를 다시
  적용하면 동일한 카탈로그가 재현되어야 한다.

### Key Entities

- **Type**: 타입의 공통 표현. 종류(entity/relation/attribute), 이름, abstract 여부, 상속
  구간 라벨을 갖는다.
- **Entity Type**: 노드의 타입. 상속 계층에 속하며 attribute 집합과 제약을 갖는다.
- **Relation Type**: 엣지의 타입. role 집합, 상속 계층, attribute 집합을 갖는다.
- **Role**: 관계 타입 안에서 참여자가 갖는 이름 있는 자리. 허용 타입과 카디널리티 제약을 갖는다.
- **Attribute Type**: 값의 타입. 값 도메인, 스칼라 타입, 상속 관계를 갖는다.
- **Inheritance Label**: 타입 계층 위치를 나타내는 구간 인코딩. 서브타입 판정의 근거.
- **Constraint**: 제약의 표현. 대상(타입/attribute/role), 종류(required, key, cardinality,
  domain), 파라미터를 갖는다.
- **Inference Rule**: 관계 특성 또는 규칙 기반 추론 정의. 활성화 여부와 적용 범위를 갖는다.
- **Schema Version**: 카탈로그 스냅샷의 버전. 변경 이력 추적과 동시성 제어의 기준.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 깊이 8·1,000개 타입 계층에서 상위 타입 질의의 타입 판정 오버헤드가 **후손 수와
  무관하게 일정**하며, 깊이 1 질의 대비 5% 이내 차이를 갖는다.
- **SC-002**: 동일 계층·동일 데이터에 대해 Neo4j에서 상위 레이블을 수동으로 중복 부여한 방식과
  비교할 때, 질의 지연시간이 **동등하거나 더 빠르다**.
- **SC-003**: 상위 타입 질의의 실행 계획에 재귀 노드가 **0개**다(자동 검증 테스트로 강제).
- **SC-004**: 1억 인스턴스 타입에 선택적 attribute 추가가 **1초 이내** 완료된다.
- **SC-005**: 계층 중간 타입 삽입이 **10초 이내** 완료되며, 그 동안 읽기 질의가 차단되지
  않는다.
- **SC-006**: 제약 위반 쓰기의 **100%** 가 거부되고, 오류 메시지에 위반 대상과 기대값이
  포함된다.
- **SC-007**: 스키마를 DDL로 내보내고 빈 데이터베이스에 재적용했을 때 카탈로그가 **100% 동일**
  하게 재현된다.
- **SC-008**: 이행적 관계 추론 질의가 동일 결과를 내는 수동 재귀 CTE 대비 **3배 이상** 빠르다.
- **SC-009**: 제약 검증으로 인한 쓰기 처리량 저하가 제약 없는 경우 대비 **15% 이내**다.

## Assumptions

- 타입 카탈로그가 정의하는 프로퍼티 슬롯 레이아웃은 스펙 **001-graph-storage-engine**이
  물리적으로 구현한다. 본 스펙은 논리 모델과 상속 인덱스를 정의한다.
- 타입 이름 해석과 상속 인덱스 활용은 스펙 **003-cypher-query-engine**의 계획 수립 단계에서
  이루어진다.
- OWL 클래스/프로퍼티 및 RDFS 서브클래스 관계는 스펙 **006-semantic-web-adapters**에서 본
  타입 모델로 매핑된다. 본 스펙의 추론 기능은 그 기반이며, 완전한 OWL 추론은 006 범위다.
- 벤치마킹 대상은 TypeDB(개념 모델·role·제약)와 Neo4j(멀티레이블 호환성)다. TypeDB의 TypeQL
  문법 자체를 채택하지는 않으며, Cypher 확장 문법으로 표현한다.
- 완전한 규칙 기반 추론(사용자 정의 Datalog 스타일 규칙)은 초기 범위가 아니며, 관계 특성
  기반 추론부터 시작한다.
- 스키마리스 사용도 계속 지원한다. 타입 시스템은 강제되는 것이 아니라 선언한 만큼 강제된다.
