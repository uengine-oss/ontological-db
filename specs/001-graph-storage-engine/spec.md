# Feature Specification: 네이티브 그래프 저장 엔진 (Native Graph Storage Engine)

**Feature Branch**: `001-graph-storage-engine`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "PostgreSQL을 상속하여 구현하되, Apache AGE와는 다르게 접근하여 Neo4j 수준의 트래버설 성능을 내는 저장 구조"

## 개요

Ontological의 성능 전체가 이 스펙에 달려 있다. Apache AGE는 노드/엣지를 일반 힙 테이블에
담고 프로퍼티를 `agtype`(JSONB 계열)으로 저장하기 때문에, 한 홉 이동이 곧 B-tree 조회 +
JSON 파싱이 된다. 홉이 깊어질수록 이 비용이 곱해진다.

이 스펙은 **인접 정보를 순차 접근 가능한 세그먼트로, 프로퍼티를 타입 카탈로그가 아는 고정
슬롯으로** 저장하는 PostgreSQL Table Access Method 기반 저장 엔진을 정의한다. MVCC·WAL·
트랜잭션은 PostgreSQL의 것을 그대로 사용한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 깊은 트래버설이 선형 비용으로 끝난다 (Priority: P1)

지식 그래프 분석가가 1,000만 노드/1억 엣지 규모의 그래프에서 특정 엔티티로부터 4홉 떨어진
연관 엔티티를 조회한다. 각 홉마다 인덱스를 다시 뒤지지 않고, 이웃 목록을 순차적으로 읽어
확장한다.

**Why this priority**: 트래버설 성능은 이 제품이 존재하는 이유다. 이것이 안 되면 나머지 스펙은
의미가 없다.

**Independent Test**: LDBC SNB 데이터셋을 적재하고 1~4홉 이웃 확장 질의의 지연시간과
버퍼 접근 횟수(`EXPLAIN (ANALYZE, BUFFERS)`)를 Apache AGE와 비교하여 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 평균 차수 50인 1억 엣지 그래프가 적재되어 있고, **When** 임의의 시작 노드에서
   1홉 이웃 전체를 조회하면, **Then** 이웃 1건당 논리 페이지 읽기가 상수에 수렴하며(차수에
   비례한 인덱스 조회가 발생하지 않으며) 동일 질의의 Apache AGE 대비 지연시간이 5배 이상
   개선된다.
2. **Given** 동일 그래프에서, **When** 홉 수를 1→2→3→4로 늘리면, **Then** 지연시간 증가가
   방문 노드 수에 대해 선형에 근접하며 홉당 상수 배 이상으로 폭증하지 않는다.
3. **Given** 특정 관계 타입만 따라가는 질의에서, **When** 그 타입의 엣지가 전체의 1%라면,
   **Then** 나머지 99% 엣지를 읽지 않는다(타입별 인접 분할).

---

### User Story 2 - 프로퍼티 읽기에 파싱 비용이 없다 (Priority: P1)

애플리케이션이 수백만 노드의 특정 프로퍼티 두 개만 읽어 집계한다. 노드마다 JSON 문서를 풀어
헤치지 않고 필요한 슬롯만 읽는다.

**Why this priority**: `agtype`/JSONB의 per-row 파싱 비용은 대량 스캔에서 지배적이다. 타입
시스템(002)이 스키마를 알고 있으므로 이 비용은 제거 가능하다.

**Independent Test**: 20개 프로퍼티를 가진 500만 노드에서 2개 프로퍼티만 집계하는 질의를
실행하고, 읽은 바이트 수와 CPU 시간을 전체 프로퍼티 저장 방식과 비교한다.

**Acceptance Scenarios**:

1. **Given** 20개 프로퍼티를 가진 타입의 노드 500만 개가 있고, **When** 그중 2개 프로퍼티만
   집계하면, **Then** 나머지 18개 프로퍼티의 값을 역직렬화하지 않는다.
2. **Given** 고정폭 프로퍼티(정수, 실수, 불리언, 타임스탬프)만 접근하는 질의에서, **When**
   값을 읽으면, **Then** 오프셋 계산만으로 접근되며 가변길이 디코딩이 발생하지 않는다.
3. **Given** 큰 텍스트 프로퍼티를 가진 노드에서, **When** 그 프로퍼티를 참조하지 않는 질의를
   실행하면, **Then** 해당 데이터 페이지를 읽지 않는다.

---

### User Story 3 - 쓰기가 그래프 구조를 깨뜨리지 않는다 (Priority: P1)

운영 중 노드와 엣지가 계속 삽입·수정·삭제된다. 동시 트랜잭션이 서로를 보지 못하고, 서버가
비정상 종료해도 인접 구조가 손상되지 않는다.

**Why this priority**: 헌법 원칙 IX(ACID 비협상). 읽기 성능만 좋고 쓰기가 불안정한 저장 엔진은
채택할 수 없다.

**Independent Test**: 동시 쓰기 워크로드 중 강제 종료(kill -9) 후 재기동하여 인접 구조와
노드/엣지 집합의 정합성을 검증한다.

**Acceptance Scenarios**:

1. **Given** 트랜잭션 A가 엣지를 추가하고 커밋하지 않은 상태에서, **When** 트랜잭션 B가 해당
   시작 노드의 이웃을 조회하면, **Then** 그 엣지는 보이지 않는다.
2. **Given** 대량 쓰기 진행 중 서버가 비정상 종료되고, **When** 재기동하면, **Then** 복구 후
   모든 인접 구조가 커밋된 엣지 집합과 정확히 일치한다(dangling/누락 없음).
3. **Given** 엣지가 삭제되고 진공(vacuum)이 수행되면, **When** 인접 세그먼트를 스캔하면,
   **Then** 삭제된 항목이 회수되고 공간이 재사용된다.
4. **Given** 그래프에 데이터가 있는 상태에서, **When** `pg_dump` 후 새 인스턴스에 복원하면,
   **Then** 모든 노드·엣지·인접 구조·프로퍼티가 동일하게 재현된다.

---

### User Story 4 - 대량 적재가 실용적인 시간에 끝난다 (Priority: P2)

데이터 엔지니어가 1억 엣지 규모의 초기 데이터셋을 적재한다. 한 건씩 트랜잭션을 도는 대신
벌크 경로를 사용해 인접 구조를 한 번에 구축한다.

**Why this priority**: 초기 적재가 며칠 걸리면 평가 자체가 불가능하다. 다만 P1 읽기/쓰기
경로가 먼저 존재해야 의미가 있다.

**Independent Test**: 표준 형식(CSV/Parquet) 데이터셋 적재 처리량(엣지/초)을 측정한다.

**Acceptance Scenarios**:

1. **Given** 정렬되지 않은 1억 엣지 입력이 주어지고, **When** 벌크 적재를 수행하면,
   **Then** 적재 완료 시점에 인접 세그먼트가 지역성 최적 배치로 구축되어 있다.
2. **Given** 벌크 적재 중 오류가 발생하면, **When** 트랜잭션을 롤백하면, **Then** 부분 적재된
   데이터가 남지 않는다.

---

### User Story 5 - 그래프가 오래 살아도 성능이 유지된다 (Priority: P2)

수개월간 삽입·삭제가 반복된 그래프에서도 트래버설 지연이 초기 대비 크게 나빠지지 않는다.
필요 시 온라인 재조직(reorganize)으로 지역성을 회복한다.

**Why this priority**: 인접 구조 기반 저장의 알려진 약점이 단편화다. 대응책이 스펙에 없으면
운영에서 무너진다.

**Independent Test**: 삽입/삭제를 반복해 인위적으로 단편화시킨 뒤 트래버설 지연 저하율을
측정하고, 재조직 후 회복률을 확인한다.

**Acceptance Scenarios**:

1. **Given** 전체 엣지의 30%가 삭제되고 40%가 새로 삽입된 그래프에서, **When** 트래버설을
   수행하면, **Then** 지연시간 저하가 초기 대비 2배를 넘지 않는다.
2. **Given** 단편화된 그래프에서, **When** 온라인 재조직을 실행하면, **Then** 읽기·쓰기를
   차단하지 않고 진행되며 완료 후 지연시간이 초기 수준의 20% 이내로 회복된다.

---

### Edge Cases

- **슈퍼노드**: 차수가 1,000만인 노드의 이웃을 조회할 때 — 인접 세그먼트가 청크로 분할되어
  스트리밍 가능해야 하며, 특정 관계 타입/방향으로 청크 단위 프루닝이 가능해야 한다.
- **차수 0 노드**: 인접 세그먼트가 할당되지 않아도 조회가 빈 결과를 즉시 반환해야 한다.
- **자기 루프 및 다중 엣지**: 동일 노드 쌍 사이 같은 타입의 엣지가 여러 개 존재할 수 있으며,
  각각 고유 식별자를 갖는다.
- **극단적으로 큰 프로퍼티**: 개별 값이 페이지 크기를 넘을 때 TOAST 경로로 넘어가되, 해당
  프로퍼티를 참조하지 않는 질의는 영향을 받지 않아야 한다.
- **동시 구조 변경**: 두 트랜잭션이 같은 노드의 인접 구조를 동시에 수정할 때 데드락 없이
  직렬화되어야 한다.
- **식별자 고갈**: 그래프당 노드/엣지 식별자 공간이 소진될 때의 동작이 정의되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

**저장 구조**

- **FR-001**: 시스템은 노드와 엣지를 PostgreSQL Table Access Method로 구현된 전용 저장소에
  보관해야 하며, 일반 힙 테이블 + JSONB 조합에 의존해서는 안 된다.
- **FR-002**: 시스템은 각 노드에 대해 인접 엣지를 **순차 접근 가능한 인접 세그먼트**로
  저장해야 하며, 이웃 하나를 얻는 데 별도 인덱스 조회가 필요해서는 안 된다.
- **FR-003**: 인접 세그먼트는 **방향(outgoing/incoming)과 관계 타입별로 분할**되어, 특정
  방향·타입만 필요한 질의가 나머지를 읽지 않아야 한다.
- **FR-004**: 시스템은 노드·엣지 식별자를 (그래프 ID, 타입 ID, 지역 오프셋)이 인코딩된
  고정폭 정수로 표현해야 하며, 트래버설 중 문자열 비교가 발생해서는 안 된다.
- **FR-005**: 프로퍼티는 타입 카탈로그(002)가 정의한 스키마에 따라 슬롯 기반으로 저장되어야
  하며, 고정폭 값은 오프셋 계산만으로 접근 가능해야 한다.
- **FR-006**: 시스템은 선언되지 않은(ad-hoc) 프로퍼티를 오버플로 영역에 저장하여 지원해야
  하되, 이것이 선언된 프로퍼티의 접근 비용을 증가시켜서는 안 된다.
- **FR-007**: 시스템은 프로퍼티를 **컬럼 지향으로 읽을 수 있어야** 하며, 참조되지 않은
  프로퍼티의 데이터 페이지를 읽지 않아야 한다.

**트랜잭션 및 내구성**

- **FR-008**: 모든 그래프 구조 변경은 PostgreSQL MVCC 가시성 규칙을 따라야 한다.
- **FR-009**: 모든 그래프 구조 변경은 WAL에 기록되어야 하며, crash recovery 후 인접 구조가
  커밋된 데이터와 정확히 일치해야 한다.
- **FR-010**: 시스템은 `pg_dump`/`pg_restore`, PITR, 물리 복제와 정합해야 한다.
- **FR-011**: 삭제된 노드/엣지의 공간은 vacuum 경로를 통해 회수되어 재사용되어야 한다.
- **FR-012**: 엣지 삽입/삭제 시 양 끝 노드의 인접 세그먼트가 동일 트랜잭션 내에서 갱신되어야
  하며, 비동기 갱신은 허용되지 않는다.

**스캔 및 접근 경로**

- **FR-013**: 시스템은 타입별 전체 노드 스캔, 타입별 전체 엣지 스캔, 식별자 기반 단건 조회,
  인접 확장 스캔을 접근 경로로 제공해야 한다.
- **FR-014**: 인접 확장 스캔은 결과를 스트리밍으로 반환해야 하며, 슈퍼노드에서 전체 이웃을
  메모리에 적재해서는 안 된다.
- **FR-015**: 시스템은 각 접근 경로에 대해 옵티마이저가 사용할 수 있는 비용 추정치(카디널리티,
  선택도, 페이지 수)를 제공해야 한다.
- **FR-016**: 시스템은 프로퍼티 인덱스(타입+프로퍼티 조합)를 지원해야 하며, PostgreSQL의
  기존 인덱스 인프라를 활용해야 한다.

**운영**

- **FR-017**: 시스템은 벌크 적재 경로를 제공해야 하며, 적재 완료 시 인접 세그먼트가 지역성
  최적으로 배치되어야 한다.
- **FR-018**: 시스템은 온라인 재조직(reorganize) 연산을 제공해야 하며, 실행 중 읽기·쓰기를
  차단해서는 안 된다.
- **FR-019**: 시스템은 그래프별 저장 통계(노드/엣지 수, 타입별 분포, 차수 분포, 단편화율,
  세그먼트 사용률)를 조회 가능한 형태로 노출해야 한다.
- **FR-020**: 시스템은 슈퍼노드를 자동 탐지하여 인접 세그먼트를 청크 분할해야 하며, 임계치는
  설정 가능해야 한다.

**제약**

- **FR-021**: 시스템은 패치되지 않은 표준 PostgreSQL 16 이상에서 `CREATE EXTENSION`으로
  설치 가능해야 하며, PostgreSQL 소스 수정을 요구해서는 안 된다.
- **FR-022**: 시스템은 단일 데이터베이스 내 복수의 독립 그래프를 지원해야 한다.

### Key Entities

- **Graph**: 독립된 노드·엣지·타입 카탈로그의 이름공간. 데이터베이스 내에 여러 개 존재 가능.
- **Node Record**: 고정폭 식별자, 타입 참조, 프로퍼티 슬롯, 인접 세그먼트 참조를 갖는 저장
  단위.
- **Edge Record**: 고정폭 식별자, 관계 타입 참조, 시작/끝 노드 식별자, role 바인딩(002),
  프로퍼티 슬롯을 갖는 저장 단위.
- **Adjacency Segment**: 한 노드의 특정 방향·관계 타입에 속하는 엣지들을 순차 배치한 저장
  블록. 차수가 크면 청크로 분할된다.
- **Property Slot Layout**: 타입 카탈로그가 정의하는 프로퍼티 → 오프셋/폭 매핑. 타입 진화 시
  버전을 갖는다.
- **Overflow Area**: 선언되지 않은 프로퍼티 및 가변길이 값의 저장 영역.
- **Segment Directory**: 노드 식별자 → 인접 세그먼트 위치를 해결하는 매핑 구조.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: LDBC SNB SF-10 데이터셋에서 1홉 이웃 확장 질의의 p95 지연시간이 동일 하드웨어의
  Apache AGE 대비 **5배 이상** 빠르다.
- **SC-002**: 동일 데이터셋 3홉 이웃 확장에서 Apache AGE 대비 **10배 이상** 빠르며, Neo4j
  Community 대비 **2배 이내**의 지연시간을 갖는다.
- **SC-003**: 20개 프로퍼티 중 2개만 읽는 집계 질의에서 읽은 바이트 수가 전체 프로퍼티를
  역직렬화하는 방식 대비 **80% 이상** 감소한다.
- **SC-004**: 1억 엣지 벌크 적재가 단일 노드(16코어/64GB 기준)에서 **60분 이내** 완료된다.
- **SC-005**: 비정상 종료 후 복구에서 인접 구조 정합성 검증이 **100회 반복 테스트에서 100%**
  통과한다.
- **SC-006**: 30% 삭제 + 40% 삽입으로 단편화된 그래프의 트래버설 지연 저하가 **2배 이내**이며,
  온라인 재조직 후 초기 대비 **20% 이내**로 회복된다.
- **SC-007**: 차수 1,000만 슈퍼노드의 상위 100개 이웃 조회가 **10ms 이내**에 첫 결과를
  반환한다(전체 인접 적재 없음).
- **SC-008**: 100 동시 쓰기 세션에서 데드락 발생률이 트랜잭션 1만 건당 1건 미만이다.

## Assumptions

- 타입 스키마(프로퍼티 슬롯 레이아웃, 관계 타입, role)는 스펙 **002-ontology-type-system**이
  정의하며, 본 스펙은 그 카탈로그를 소비한다.
- 질의 계획 수립과 연산자 실행은 스펙 **003-cypher-query-engine**이 담당하고, 본 스펙은 접근
  경로와 비용 추정치만 제공한다.
- 분산/샤딩은 스펙 **007-distributed-cluster** 범위이며, 본 스펙은 단일 노드 저장 구조를
  다룬다. 다만 식별자 인코딩은 후일 샤드 ID를 수용할 수 있는 여유 비트를 갖는다.
- 벡터 임베딩 저장은 스펙 **004-vector-hybrid-search**가 pgvector 위에서 정의하며, 본 스펙은
  프로퍼티 슬롯에서 벡터 값을 참조할 수 있게만 한다.
- 대상 배포 환경은 로컬/셀프호스트 PostgreSQL 및 Supabase를 포함한 관리형 서비스다. 관리형
  환경에서 사용 불가한 커널 기능에 의존하지 않는다.
- 초기 목표 규모는 단일 노드 기준 10억 엣지다. 그 이상은 007 범위다.
- 문자 인코딩은 UTF-8, 정렬 규칙은 데이터베이스 기본 collation을 따른다.
