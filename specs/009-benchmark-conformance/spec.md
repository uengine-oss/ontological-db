# Feature Specification: 벤치마크 및 적합성 하네스 (Benchmark & Conformance Harness)

**Feature Branch**: `009-benchmark-conformance`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "성능이 좋아야 하기 때문에... 아파치 AGE는 단순한 데이터베이스 구조로 되어 있어서 성능을 담보하지 못한다"

## 개요

이 제품의 핵심 주장은 두 가지다: **Apache AGE보다 훨씬 빠르다**, 그리고 **Neo4j에 준하는
성능과 TypeDB에 준하는 표현력을 갖는다**. 두 주장 모두 증명 없이는 마케팅 문구일 뿐이다.

이 스펙은 헌법 원칙 X("Benchmarked or It Didn't Happen")를 실행 가능한 인프라로 만든다:
표준 워크로드, 경쟁 제품 대비 자동 비교, 적합성 스위트, CI 회귀 게이트, 공개 가능한 결과.

이것은 "테스트"가 아니라 **제품 요구사항**이다. 성능 회귀를 잡지 못하는 프로젝트는 001의
설계 의도를 몇 달 안에 잃는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 성능 회귀가 병합 전에 잡힌다 (Priority: P1)

기여자가 저장 엔진을 수정한 PR을 올린다. CI가 벤치마크를 돌려 핵심 지표가 기준선 대비
악화되었음을 감지하고 병합을 차단한다. 어느 질의가 얼마나 느려졌는지 PR에 보고된다.

**Why this priority**: 회귀 게이트가 없으면 나머지 스펙의 성능 목표는 시간이 지나며 침식된다.

**Independent Test**: 의도적으로 성능을 떨어뜨리는 변경을 넣고 CI가 차단하는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 기준선이 기록된 상태에서, **When** 성능을 20% 악화시키는 변경이 PR로 올라오면,
   **Then** CI가 실패하고 악화된 질의 목록과 수치가 보고된다.
2. **Given** 측정 노이즈 범위 안의 변동만 있을 때, **When** CI가 실행되면, **Then** 실패하지
   않는다(오탐 방지).
3. **Given** 의도적인 성능 트레이드오프가 있는 PR에서, **When** 명시적 승인 표시가 있으면,
   **Then** 새 기준선으로 갱신할 수 있다.
4. **Given** CI 벤치마크가 실행되면, **When** 소요 시간을 측정하면, **Then** 개발 흐름을
   막지 않는 시간 안에 끝난다.

---

### User Story 2 - 경쟁 제품 대비 성능이 자동 측정된다 (Priority: P1)

성능 엔지니어가 한 번의 명령으로 Ontological, Apache AGE, Neo4j, 순수 PostgreSQL 재귀 CTE에
동일 워크로드를 돌리고 비교 리포트를 얻는다.

**Why this priority**: "AGE보다 빠르다"는 이 제품의 존재 근거다. 재현 가능한 비교가 없으면
주장할 수 없다.

**Independent Test**: 비교 하네스를 실행하고 리포트가 생성되는지, 다른 환경에서 재현되는지
확인한다.

**Acceptance Scenarios**:

1. **Given** 비교 하네스가 준비되어 있을 때, **When** 실행하면, **Then** 동일 데이터·동일
   질의에 대한 시스템별 지연시간·처리량 비교 리포트가 생성된다.
2. **Given** 비교 대상 시스템이 설치되어 있지 않을 때, **When** 실행하면, **Then** 컨테이너로
   자동 준비되거나 명확한 안내와 함께 해당 시스템만 건너뛴다.
3. **Given** 각 시스템에서, **When** 결과를 확인하면, **Then** 모든 시스템이 동일한 정답을
   반환했음이 검증된다(성능만 다르고 결과가 다르면 무의미).
4. **Given** 리포트가 생성되면, **When** 확인하면, **Then** 하드웨어, 설정, 데이터 규모, 버전이
   함께 기록되어 재현 가능하다.

---

### User Story 3 - 표준 벤치마크로 규모를 검증한다 (Priority: P1)

평가자가 LDBC SNB를 여러 스케일 팩터로 실행해 규모에 따른 성능 곡선을 확인한다.

**Why this priority**: 자체 제작 벤치마크는 신뢰를 얻지 못한다. 업계 표준 워크로드가 필요하다.

**Independent Test**: LDBC SNB 데이터 생성 → 적재 → Interactive/BI 질의 실행 → 결과 검증
전 과정을 자동 실행한다.

**Acceptance Scenarios**:

1. **Given** LDBC SNB 데이터 생성기가 통합되어 있을 때, **When** 스케일 팩터를 지정해
   실행하면, **Then** 데이터 생성·적재·질의 실행이 자동으로 완료된다.
2. **Given** LDBC 질의 결과가 나오면, **When** 참조 결과와 비교하면, **Then** 정확성이
   검증된다.
3. **Given** 여러 스케일 팩터(1/10/100)에서 실행하면, **When** 결과를 확인하면, **Then**
   규모에 따른 성능 곡선이 리포트에 포함된다.
4. **Given** 적재 단계에서, **When** 처리량을 측정하면, **Then** 적재 시간과 저장 공간 효율이
   기록된다.

---

### User Story 4 - Cypher 적합성이 지속적으로 측정된다 (Priority: P1)

기여자가 질의 엔진을 수정한다. openCypher TCK 통과율이 자동 측정되고, 떨어지면 병합이
차단된다. 어느 기능이 미지원인지 항상 최신 목록으로 유지된다.

**Why this priority**: 성능만큼 정확성이 중요하다. "동작하는 것처럼 보이지만 의미론이 틀린"
그래프 DB는 신뢰를 얻지 못한다.

**Independent Test**: TCK 스위트를 실행하고 통과율과 실패 목록을 확인한다.

**Acceptance Scenarios**:

1. **Given** openCypher TCK가 통합되어 있을 때, **When** 실행하면, **Then** 기능별 통과율과
   실패 시나리오 목록이 생성된다.
2. **Given** 통과율이 기준선보다 떨어지는 변경이 있을 때, **When** CI가 실행되면, **Then**
   차단되고 새로 실패한 시나리오가 보고된다.
3. **Given** TCK 결과가 있을 때, **When** 문서를 생성하면, **Then** 지원 기능 매트릭스가
   자동으로 갱신된다.
4. **Given** SPARQL·SHACL 적합성 스위트가 통합되면, **When** 실행하면, **Then** 동일한 방식의
   통과율 리포트가 생성된다.

---

### User Story 5 - 내구성과 정합성이 장애 주입으로 검증된다 (Priority: P1)

품질 담당자가 쓰기 중 강제 종료, 디스크 가득참, 네트워크 분단을 주입하고 데이터 정합성이
유지되는지 확인한다.

**Why this priority**: 헌법 원칙 IX의 검증 수단이다. 그래프 저장 구조는 인접 구조와 노드/엣지
집합이 어긋날 수 있어 일반 DB보다 검증이 더 필요하다.

**Independent Test**: 장애 주입 시나리오를 반복 실행하고 정합성 검사기로 검증한다.

**Acceptance Scenarios**:

1. **Given** 쓰기 워크로드 실행 중에, **When** 프로세스를 강제 종료하고 재기동하면, **Then**
   정합성 검사기가 인접 구조·인덱스·카탈로그의 불일치를 0건으로 보고한다.
2. **Given** 클러스터 환경에서, **When** 네트워크 분단을 주입하면, **Then** 분산 트랜잭션의
   원자성이 유지되고 조용한 부분 결과가 발생하지 않는다.
3. **Given** 정합성 검사기가 실행되면, **When** 불일치가 있으면, **Then** 어느 노드·엣지·구조에
   문제가 있는지 구체적으로 보고한다.
4. **Given** 장기 실행 스트레스 테스트에서, **When** 24시간 이상 실행하면, **Then** 메모리
   누수와 공간 누수가 발생하지 않는다.

---

### User Story 6 - 에이전트 정확도가 측정된다 (Priority: P2)

제품 담당자가 "에이전트가 이 DB를 얼마나 잘 쓰는가"를 수치로 확인한다. 자연어 질문 세트에
대한 질의 생성 성공률과 정답률이 릴리스마다 추적된다.

**Why this priority**: 스펙 008의 성공 기준을 검증하는 유일한 방법이다. 다만 코어 성능·정확성이
먼저다.

**Independent Test**: 표준 질문 세트로 참조 에이전트를 실행하고 성공률을 측정한다.

**Acceptance Scenarios**:

1. **Given** 자연어 질문 세트와 정답이 준비되어 있을 때, **When** 참조 에이전트를 실행하면,
   **Then** 1회 성공률, 재시도 후 성공률, 정답률이 리포트된다.
2. **Given** 스키마 요약 형식을 변경하면, **When** 재측정하면, **Then** 변화가 수치로 확인된다.
3. **Given** 여러 LLM 모델에서, **When** 실행하면, **Then** 모델별 결과가 비교 가능하다.

---

### User Story 7 - 결과가 공개되고 재현 가능하다 (Priority: P2)

외부 평가자가 공개된 벤치마크 결과를 자신의 환경에서 재현한다. 하네스, 데이터, 설정, 절차가
모두 저장소에 있다.

**Why this priority**: 재현 불가능한 벤치마크는 신뢰를 얻지 못하고, 오히려 의심을 산다.

**Independent Test**: 깨끗한 환경에서 문서만 보고 벤치마크를 재현한다.

**Acceptance Scenarios**:

1. **Given** 저장소를 클론한 외부 사용자가, **When** 문서의 절차를 따르면, **Then** 공개
   결과와 동등한 수치를 재현한다(하드웨어 차이는 정규화).
2. **Given** 벤치마크 결과가 발표되면, **When** 확인하면, **Then** 사용된 설정·튜닝 파라미터가
   모두 공개되어 있다.
3. **Given** 시간에 따른 결과가 축적되면, **When** 조회하면, **Then** 버전별 성능 추이를 볼 수
   있다.

---

### Edge Cases

- **측정 노이즈**: 클라우드 CI 환경의 성능 변동이 회귀 판정을 오염시킬 때 — 통계적 판정과
  반복 측정이 필요하다.
- **불공정 비교**: 경쟁 제품이 기본 설정으로만 측정되어 불리해지는 경우 — 각 시스템의 권장
  튜닝을 적용하고 그 내용을 공개해야 한다.
- **결과 불일치**: 시스템 간 정답이 다를 때 성능 비교는 무효 처리되어야 한다.
- **하드웨어 의존**: 결과가 특정 하드웨어에서만 성립할 때 — 최소 2종 이상 환경에서 검증.
- **워크로드 과적합**: CI 벤치마크 질의에만 최적화되는 것을 막기 위한 홀드아웃 질의 집합.
- **LLM 비결정성**: 에이전트 정확도 측정의 분산 — 반복 실행과 신뢰구간 보고.
- **거대 스케일 팩터**: SF-1000 같은 규모의 CI 실행 불가 — 정기(nightly/weekly) 실행 분리.

## Requirements *(mandatory)*

### Functional Requirements

**워크로드**

- **FR-001**: 시스템은 LDBC SNB(Interactive, BI) 데이터 생성기와 질의 집합을 통합해야 한다.
- **FR-002**: 시스템은 최소 스케일 팩터 1, 10, 100을 지원해야 하며, 더 큰 규모는 선택적으로
  실행 가능해야 한다.
- **FR-003**: 시스템은 제품 고유 기능(상속 질의, 관계 벡터 검색, 하이브리드 검색, 추론)에 대한
  자체 마이크로 벤치마크를 제공해야 한다.
- **FR-004**: 시스템은 CI용 홀드아웃 질의 집합을 유지해 최적화 과적합을 탐지해야 한다.
- **FR-005**: 시스템은 적재 처리량과 저장 공간 효율을 측정해야 한다.

**비교**

- **FR-006**: 시스템은 Apache AGE, Neo4j(Community), 순수 PostgreSQL 재귀 CTE를 비교 대상으로
  자동 실행할 수 있어야 한다.
- **FR-007**: 비교 대상 환경은 컨테이너 등으로 재현 가능하게 구성되어야 한다.
- **FR-008**: 비교 실행 전 모든 시스템이 동일한 정답을 반환하는지 검증해야 하며, 불일치 시
  성능 비교를 무효 처리해야 한다.
- **FR-009**: 각 시스템에는 문서화된 권장 튜닝이 적용되어야 하며, 적용 내용이 리포트에
  포함되어야 한다.
- **FR-010**: 리포트에는 하드웨어, OS, 버전, 설정, 데이터 규모가 기록되어야 한다.

**적합성**

- **FR-011**: 시스템은 openCypher TCK를 통합하고 기능별 통과율과 실패 목록을 산출해야 한다.
- **FR-012**: 시스템은 SPARQL 1.1 및 SHACL 테스트 스위트를 통합해야 한다.
- **FR-013**: 적합성 결과로부터 지원 기능 매트릭스 문서가 자동 생성되어야 한다.
- **FR-014**: 적합성 통과율의 기준선이 저장소에 기록되고, 회귀 시 CI가 차단해야 한다.

**정합성과 내구성**

- **FR-015**: 시스템은 그래프 정합성 검사기를 제공해야 하며, 인접 구조·노드/엣지 집합·인덱스·
  타입 카탈로그 간 불일치를 탐지해야 한다.
- **FR-016**: 시스템은 장애 주입 시나리오(프로세스 강제 종료, 디스크 가득참, 네트워크 분단,
  노드 장애)를 자동 실행해야 한다.
- **FR-017**: 시스템은 장시간 스트레스 테스트를 제공하고 메모리·공간 누수를 탐지해야 한다.
- **FR-018**: 시스템은 백업/복원/복제/업그레이드 사이클을 자동 검증해야 한다.

**CI 게이트**

- **FR-019**: CI는 PR마다 축약 벤치마크를 실행하고, 기준선 대비 유의미한 회귀 시 차단해야 한다.
- **FR-020**: 회귀 판정은 반복 측정과 통계적 기준을 사용해 노이즈로 인한 오탐을 억제해야 한다.
- **FR-021**: CI 벤치마크는 개발 흐름을 막지 않는 시간 안에 완료되어야 하며, 전체 벤치마크는
  정기 실행으로 분리되어야 한다.
- **FR-022**: 기준선 갱신은 명시적 승인 절차를 통해서만 가능해야 한다.
- **FR-023**: CI 실패 시 어떤 질의가 얼마나 회귀했는지 PR에 보고되어야 한다.

**에이전트 평가**

- **FR-024**: 시스템은 자연어 질문 + 정답 세트를 포함한 에이전트 평가 데이터셋을 제공해야 한다.
- **FR-025**: 시스템은 참조 에이전트 구현으로 질의 생성 성공률·재시도 후 성공률·정답률을
  측정해야 한다.
- **FR-026**: 에이전트 평가는 복수 모델에 대해 실행 가능해야 하며, LLM 비결정성을 고려해 반복
  실행과 신뢰구간을 보고해야 한다.

**리포팅**

- **FR-027**: 모든 벤치마크 결과는 기계 판독 가능한 형식과 사람이 읽는 리포트 두 가지로
  생성되어야 한다.
- **FR-028**: 결과는 시간에 따라 축적되어 버전별 성능 추이를 조회할 수 있어야 한다.
- **FR-029**: 하네스, 데이터 생성 절차, 설정, 실행 방법이 저장소에 공개되어 외부 재현이
  가능해야 한다.
- **FR-030**: 공개 발표되는 모든 성능 수치는 하네스로 재현 가능해야 하며, 재현 절차가 함께
  제공되어야 한다.

### Key Entities

- **Workload**: 벤치마크 워크로드 정의. 데이터셋, 질의 집합, 스케일 팩터, 실행 파라미터.
- **Baseline**: 기준선 성능 수치와 그 측정 환경. 버전과 승인 이력을 갖는다.
- **Benchmark Run**: 한 번의 실행 결과. 환경 정보, 지표, 원시 측정값.
- **Comparison Report**: 시스템 간 비교 결과와 정답 일치 검증 결과.
- **Conformance Result**: 적합성 스위트 통과율, 실패 시나리오 목록, 기능 매트릭스.
- **Integrity Checker**: 그래프 내부 구조 정합성 검사기와 그 보고서.
- **Fault Scenario**: 장애 주입 시나리오 정의와 기대 결과.
- **Agent Eval Set**: 자연어 질문, 정답, 평가 기준.
- **Regression Verdict**: CI 회귀 판정 결과와 통계적 근거.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 20% 성능 악화를 주입한 변경이 CI에서 **100% 탐지**된다.
- **SC-002**: 변경 없는 PR에서 회귀 오탐율이 **5% 미만**이다.
- **SC-003**: CI 축약 벤치마크가 **15분 이내** 완료된다.
- **SC-004**: 비교 하네스가 단일 명령으로 **4개 시스템**(Ontological, AGE, Neo4j, PostgreSQL
  재귀 CTE) 전부를 실행하고 리포트를 생성한다.
- **SC-005**: 비교 실행에서 시스템 간 결과 정확성 검증이 **자동으로 수행**되며, 불일치 시
  성능 수치가 무효 처리된다.
- **SC-006**: LDBC SNB SF-10 전체 사이클(생성 → 적재 → 실행 → 검증)이 **자동으로 완료**된다.
- **SC-007**: openCypher TCK 통과율이 **매 커밋마다 측정**되며 기준선 회귀가 차단된다.
- **SC-008**: 장애 주입 후 정합성 검사에서 불일치가 **100회 반복 중 0건**이다.
- **SC-009**: 24시간 스트레스 테스트에서 메모리·공간 누수가 **탐지되지 않는다**.
- **SC-010**: 외부 사용자가 문서만으로 벤치마크를 재현했을 때 결과 편차가 **동일 하드웨어
  기준 10% 이내**다.
- **SC-011**: 지원 기능 매트릭스 문서가 적합성 결과로부터 **자동 생성**되며 수동 갱신이
  불필요하다.
- **SC-012**: 에이전트 평가가 **최소 3개 모델**에 대해 실행되고 신뢰구간과 함께 보고된다.

## Assumptions

- 본 스펙은 다른 모든 스펙의 성공 기준을 **검증하는 인프라**다. 각 스펙의 SC 항목이 본 하네스의
  측정 대상이 된다.
- 성능 목표 수치 자체는 각 스펙(001, 003, 004, 007)이 정의하고, 본 스펙은 그 측정 방법과
  게이트를 정의한다.
- Neo4j Community Edition을 비교 대상으로 사용한다. Enterprise 기능(클러스터링 등)과의 비교는
  라이선스 제약을 확인한 뒤 별도로 다룬다.
- LDBC SNB의 공식 검증 절차(auditing)는 초기 범위 밖이며, 비공식 실행으로 시작한다.
- TypeDB는 개념 모델 벤치마킹 대상이지만 성능 비교 대상으로는 초기 범위에 넣지 않는다(질의
  언어가 달라 공정한 비교 워크로드 구성이 별도 과제).
- CI 실행 환경의 성능 변동을 고려해, 절대 수치가 아닌 **동일 실행 내 상대 비교**를 회귀 판정
  기준으로 삼는다.
- 에이전트 평가에 사용하는 LLM 호출 비용은 정기 실행으로 제한하며, PR마다 실행하지 않는다.
- 공개 벤치마크 결과 발표는 마케팅이 아니라 검증 가능성을 목적으로 한다. 불리한 결과도 함께
  공개한다.
