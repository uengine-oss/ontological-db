# Feature Specification: 분산 클러스터와 확장성 (Distributed Cluster & Scale-Out)

**Feature Branch**: `007-distributed-cluster`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "우리는 클러스터링이 가능해야 한다. 그래서 확장성이 담보되어야 한다"

## 개요

단일 노드 성능(001)만으로는 한계가 있다. 그래프는 특히 어렵다 — 데이터를 나누면 엣지가
노드 경계를 가로지르고, 트래버설 한 홉이 네트워크 왕복이 된다. 순진한 샤딩은 단일 노드보다
느려진다.

이 스펙은 **그래프 인지적 파티셔닝 + 연산 push-down**으로 확장하는 클러스터를 정의한다.
핵심 규칙 두 가지: (1) 홉마다 데이터를 코디네이터로 끌어오지 않는다, (2) 단일 노드 배포는
분산 코드 경로 때문에 느려지지 않는다(헌법 원칙 VII).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 읽기 부하를 복제로 확장한다 (Priority: P1)

서비스 운영자가 읽기 질의가 폭증하자 읽기 복제본을 추가한다. 애플리케이션은 연결 문자열만
바꾸면 되고, 그래프 질의가 복제본에서 동일하게 동작한다.

**Why this priority**: 가장 흔한 확장 요구이며, PostgreSQL 물리 복제를 그대로 상속하므로
가장 빨리 제공 가능하다. 샤딩 없이도 상당한 확장을 준다.

**Independent Test**: 복제본을 추가하며 읽기 처리량 확장성과 복제 지연을 측정한다.

**Acceptance Scenarios**:

1. **Given** 스트리밍 복제가 설정된 상태에서, **When** 복제본에 그래프 읽기 질의를 실행하면,
   **Then** 주 서버와 동일한 결과가 반환된다.
2. **Given** 읽기 복제본을 3개로 늘리면, **When** 읽기 부하를 분산하면, **Then** 총 읽기
   처리량이 거의 선형으로 증가한다.
3. **Given** 주 서버에서 그래프를 변경하면, **When** 복제 지연을 측정하면, **Then** 일반
   관계형 데이터와 동등한 수준의 지연을 갖는다.
4. **Given** 주 서버 장애가 발생하면, **When** 승격(failover)이 수행되면, **Then** 그래프
   데이터 손실 없이 서비스가 재개된다.

---

### User Story 2 - 데이터를 샤딩해 쓰기와 용량을 확장한다 (Priority: P1)

플랫폼 팀이 단일 노드 용량을 넘는 그래프를 여러 노드에 분산한다. 애플리케이션 질의는 그대로
동작하고, 어느 샤드에 무엇이 있는지 신경 쓰지 않는다.

**Why this priority**: 사용자가 요구한 "확장성 담보"의 본체다.

**Independent Test**: 동일 데이터셋을 1/2/4/8 노드에 분산하고 적재 처리량, 용량, 질의 지연을
측정한다.

**Acceptance Scenarios**:

1. **Given** 그래프가 여러 노드에 분산되어 있고, **When** 클라이언트가 표준 Cypher 질의를
   실행하면, **Then** 샤드 위치를 명시하지 않고도 정확한 결과가 반환된다.
2. **Given** 노드를 2개에서 4개로 늘리면, **When** 쓰기 처리량을 측정하면, **Then**
   처리량이 증가하고 각 노드의 저장 용량이 줄어든다.
3. **Given** 단일 샤드 안에서 완결되는 질의가 있을 때, **When** 실행하면, **Then** 다른
   샤드와 통신하지 않는다.
4. **Given** 분산 트랜잭션이 여러 샤드를 변경할 때, **When** 커밋하면, **Then** 원자적으로
   반영되거나 전체가 롤백된다.

---

### User Story 3 - 트래버설이 네트워크에 잡아먹히지 않는다 (Priority: P1)

성능 엔지니어가 3홉 질의를 분산 환경에서 실행한다. 각 홉의 확장·필터·집계가 데이터가 있는
노드에서 수행되고, 네트워크로는 축소된 결과만 흐른다.

**Why this priority**: 여기서 실패하면 분산이 오히려 손해다. 이 스펙의 성패를 가르는 지점이다.

**Independent Test**: 홉 수와 필터 선택도를 바꿔가며 네트워크 전송량과 지연을 측정하고,
코디네이터 pull 방식과 비교한다.

**Acceptance Scenarios**:

1. **Given** 다중 홉 질의가 여러 샤드에 걸칠 때, **When** 실행 계획을 확인하면, **Then**
   확장·필터·집계가 원격 노드로 push-down 된 계획이 선택된다.
2. **Given** 마지막 홉에서 강한 필터가 적용되는 질의에서, **When** 네트워크 전송량을 측정하면,
   **Then** 중간 결과 전체가 아니라 필터링된 결과만 전송된다.
3. **Given** 집계 질의가 여러 샤드에 걸칠 때, **When** 실행하면, **Then** 부분 집계가 각
   노드에서 수행되고 코디네이터는 병합만 한다.
4. **Given** 샤드 간 통신이 필요한 홉에서, **When** 여러 노드로부터 데이터를 가져와야 하면,
   **Then** 요청이 배치로 묶여 왕복 횟수가 홉당 상수에 수렴한다.

---

### User Story 4 - 파티셔닝이 엣지 컷을 줄인다 (Priority: P2)

데이터 아키텍트가 해시 분산 대신 그래프 구조를 반영한 배치를 선택한다. 함께 조회되는 노드가
같은 샤드에 모여 샤드 간 통신이 줄어든다.

**Why this priority**: 성능 차이가 크지만, 기본 샤딩과 push-down이 먼저 동작해야 한다.

**Independent Test**: 동일 워크로드를 해시 분산과 그래프 인지 분산으로 각각 실행해 샤드 간
통신량과 지연을 비교한다.

**Acceptance Scenarios**:

1. **Given** 커뮤니티 구조가 뚜렷한 그래프에서, **When** 그래프 인지 파티셔닝을 적용하면,
   **Then** 해시 분산 대비 샤드 간 엣지 비율이 유의미하게 감소한다.
2. **Given** 파티션 키를 명시적으로 지정할 때(예: 테넌트 ID), **When** 적재하면, **Then**
   같은 키의 데이터가 같은 샤드에 배치된다.
3. **Given** 데이터 분포가 시간이 지나 치우칠 때, **When** 재배치를 실행하면, **Then**
   온라인으로 수행되며 질의가 계속 가능하다.
4. **Given** 자주 함께 접근되는 노드가 있을 때, **When** 배치 최적화를 적용하면, **Then**
   해당 노드들의 동일 샤드 배치 비율이 증가한다.

---

### User Story 5 - 노드 추가/제거가 운영 중에 가능하다 (Priority: P2)

운영자가 트래픽 증가에 대응해 노드를 추가한다. 서비스를 멈추지 않고 데이터가 재분배된다.
노드 장애 시 자동으로 복구된다.

**Why this priority**: 확장성이 "재적재해야 가능"하면 실용성이 없다.

**Independent Test**: 부하 상태에서 노드를 추가·제거하고 가용성, 오류율, 재분배 소요 시간을
측정한다.

**Acceptance Scenarios**:

1. **Given** 부하가 걸린 클러스터에서, **When** 노드를 추가하면, **Then** 데이터 재분배가
   온라인으로 진행되고 질의 오류가 발생하지 않는다.
2. **Given** 노드 하나가 장애로 응답하지 않을 때, **When** 복제본이 있으면, **Then** 자동
   전환되어 질의가 계속된다.
3. **Given** 복제본이 없는 샤드가 장애일 때, **When** 그 샤드를 필요로 하는 질의가 실행되면,
   **Then** 부분 결과를 조용히 반환하지 않고 명확한 오류를 반환한다.
4. **Given** 재분배 진행 중에, **When** 쓰기가 발생하면, **Then** 데이터 손실이나 중복이
   발생하지 않는다.

---

### User Story 6 - 분산 환경에서 벡터 검색이 정확하다 (Priority: P2)

AI 애플리케이션이 샤딩된 그래프에서 top-k 벡터 검색을 실행한다. 각 샤드의 부분 결과가 병합돼
전역 top-k가 정확히 반환된다.

**Why this priority**: 004의 기능이 분산에서 깨지면 제품의 핵심 가치가 무너진다.

**Independent Test**: 분산 top-k 결과를 단일 노드 정확 결과와 비교해 재현율을 측정한다.

**Acceptance Scenarios**:

1. **Given** 벡터가 여러 샤드에 분산되어 있을 때, **When** top-k 검색을 실행하면, **Then**
   전역 top-k가 반환되며 단일 노드 결과 대비 재현율이 목표치 이상이다.
2. **Given** 필터가 특정 샤드에만 해당할 때, **When** 검색하면, **Then** 관련 없는 샤드는
   조회하지 않는다.

---

### User Story 7 - 단일 노드 성능이 희생되지 않는다 (Priority: P1)

단일 노드로 운영하는 사용자가 분산 기능을 켜지 않는다. 분산 계층 때문에 느려지지 않는다.

**Why this priority**: 헌법 원칙 VII의 명시적 요구다. 대다수 사용자가 단일 노드로 시작한다.

**Independent Test**: 분산 계층 유무에 따른 단일 노드 벤치마크를 비교한다.

**Acceptance Scenarios**:

1. **Given** 분산 기능이 비활성화된 단일 노드에서, **When** 벤치마크를 실행하면, **Then**
   분산 계층이 없는 빌드와 성능 차이가 무시 가능한 수준이다.
2. **Given** 단일 노드 배포에서, **When** 질의 계획을 확인하면, **Then** 분산 관련 연산자가
   계획에 나타나지 않는다.

---

### Edge Cases

- **슈퍼노드의 분산**: 차수 1,000만 노드가 한 샤드에 몰릴 때 — 인접 구조 자체의 분할 전략이
  필요하다.
- **네트워크 분단**: 코디네이터가 일부 샤드를 볼 수 없을 때 — 조용한 부분 결과 반환은 금지,
  명확한 오류.
- **분산 데드락**: 여러 샤드를 서로 다른 순서로 잠그는 트랜잭션의 탐지와 해소.
- **시계 편차**: 스냅샷 일관성을 위한 시각 동기화 의존성과 그 한계.
- **재분배 중 장애**: 데이터 이동 도중 노드가 죽었을 때의 복구 절차.
- **핫스팟**: 특정 샤드에 부하가 집중될 때의 탐지와 대응.
- **버전 불일치**: 클러스터 노드 간 확장 버전이 다를 때의 동작.
- **경로 질의의 전역성**: 최단 경로처럼 본질적으로 전역적인 연산의 분산 실행 전략과 한계.

## Requirements *(mandatory)*

### Functional Requirements

**복제**

- **FR-001**: 시스템은 PostgreSQL 물리 복제를 통한 읽기 확장을 지원해야 하며, 복제본에서
  그래프 읽기 질의가 정상 동작해야 한다.
- **FR-002**: 복제본의 그래프 질의 결과는 해당 시점 스냅샷에서 주 서버와 일치해야 한다.
- **FR-003**: 시스템은 주 서버 장애 시 승격 절차를 지원해야 하며, 그래프 구조의 정합성이
  유지되어야 한다.

**샤딩**

- **FR-004**: 시스템은 그래프 데이터를 복수 노드에 분산 저장하는 샤딩을 지원해야 한다.
- **FR-005**: 클라이언트 질의는 샤드 위치를 인지하지 않고 작성 가능해야 한다(위치 투명성).
- **FR-006**: 시스템은 해시 기반 분산과 명시적 파티션 키 기반 분산(예: 테넌트) 두 방식을
  지원해야 한다.
- **FR-007**: 시스템은 그래프 구조를 반영한 배치(엣지 컷 최소화)를 선택적으로 지원해야 한다.
- **FR-008**: 노드/엣지 식별자는 샤드 정보를 포함하거나 샤드 해석이 가능해야 하며, 재분배
  후에도 안정적이어야 한다.
- **FR-009**: 시스템은 슈퍼노드의 인접 구조를 복수 샤드에 분할 배치할 수 있어야 한다.

**분산 질의 실행**

- **FR-010**: 시스템은 필터, 프로젝션, 확장, 부분 집계를 데이터가 있는 노드로 push-down 해야
  한다.
- **FR-011**: 코디네이터로의 데이터 전송은 축소된 결과여야 하며, 홉마다 중간 결과 전체를
  끌어오는 방식은 금지한다.
- **FR-012**: 샤드 간 요청은 배치로 묶여야 하며, 왕복 횟수가 결과 행 수에 비례해서는 안 된다.
- **FR-013**: 분산 실행 계획은 `EXPLAIN` 으로 확인 가능해야 하며, 어느 연산이 어느 노드에서
  실행되는지 표시되어야 한다.
- **FR-014**: 단일 샤드로 해결 가능한 질의는 다른 샤드와 통신하지 않아야 한다.
- **FR-015**: 분산 벡터 top-k 검색은 각 샤드의 부분 결과를 병합해 전역 top-k를 반환해야 한다.
- **FR-016**: 전역성이 본질적인 연산(최단 경로, 전역 중심성)에 대해서는 분산 알고리즘 또는
  명시적 한계를 문서화해야 한다.

**일관성과 트랜잭션**

- **FR-017**: 여러 샤드를 변경하는 트랜잭션은 원자적으로 커밋되거나 전체 롤백되어야 한다.
- **FR-018**: 분산 질의는 일관된 스냅샷에서 실행되어야 한다.
- **FR-019**: 시스템은 분산 데드락을 탐지하고 해소해야 한다.
- **FR-020**: 노드 장애로 결과가 불완전할 수 있는 경우, 시스템은 부분 결과를 조용히 반환하지
  않고 명확한 오류를 반환해야 한다.

**탄력성과 운영**

- **FR-021**: 노드 추가/제거 시 데이터 재분배가 온라인으로 수행되어야 하며, 질의 가용성이
  유지되어야 한다.
- **FR-022**: 재분배 중 발생한 쓰기는 손실·중복 없이 처리되어야 한다.
- **FR-023**: 시스템은 노드 장애를 탐지하고, 복제본이 있으면 자동 전환해야 한다.
- **FR-024**: 시스템은 샤드별 부하·용량·핫스팟 지표를 노출해야 한다.
- **FR-025**: 시스템은 클러스터 토폴로지(노드 목록, 샤드 배치, 복제 상태)를 조회 가능한
  형태로 제공해야 한다.
- **FR-026**: 시스템은 재분배 진행 상황을 조회 가능해야 하며, 중단·재개가 가능해야 한다.

**단일 노드 보호**

- **FR-027**: 분산 계층은 opt-in이어야 하며, 비활성화 시 질의 계획에 분산 연산자가 나타나서는
  안 된다.
- **FR-028**: 분산 계층 활성화 여부와 무관하게 단일 노드 성능이 저하되어서는 안 된다.

**보안**

- **FR-029**: 접근 정책(005)은 분산 환경에서도 동일하게 적용되어야 하며, 원격 노드 실행 시에도
  우회되어서는 안 된다.
- **FR-030**: 노드 간 통신은 암호화 가능해야 하며, 노드 인증이 이루어져야 한다.

### Key Entities

- **Cluster Topology**: 노드 목록, 역할(코디네이터/워커), 상태, 버전.
- **Shard**: 그래프 데이터의 분할 단위. 배치 노드, 복제본, 크기, 부하 지표를 갖는다.
- **Placement Policy**: 데이터를 샤드에 배치하는 규칙(해시, 파티션 키, 그래프 인지).
- **Distributed Plan**: 어느 연산이 어느 노드에서 실행되는지 담은 실행 계획.
- **Remote Exchange Operator**: 노드 간 데이터 이동을 담당하는 실행 연산자. 배치 크기와
  전송량을 기록한다.
- **Distributed Transaction**: 여러 샤드에 걸친 트랜잭션의 상태와 커밋 프로토콜 진행 상황.
- **Rebalance Job**: 데이터 재분배 작업의 상태, 진행률, 중단/재개 지점.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 읽기 복제본 4개 구성에서 읽기 처리량이 단일 노드 대비 **3.5배 이상** 증가한다.
- **SC-002**: 8노드 클러스터에서 적재 처리량이 단일 노드 대비 **5배 이상** 증가한다.
- **SC-003**: 8노드 클러스터가 단일 노드 대비 **8배 규모**의 그래프를 수용한다.
- **SC-004**: 강한 필터를 가진 3홉 분산 질의에서 네트워크 전송량이 코디네이터 pull 방식 대비
  **90% 이상** 감소한다.
- **SC-005**: 다중 홉 분산 질의의 샤드 간 왕복 횟수가 **홉당 상수**이며 결과 행 수에 비례하지
  않는다.
- **SC-006**: 그래프 인지 파티셔닝이 해시 분산 대비 샤드 간 엣지 비율을 **40% 이상** 감소시킨다.
- **SC-007**: 부하 상태에서 노드 추가 시 질의 오류율이 **0%** 이고, 지연시간 증가가 **50% 이내**
  로 유지된다.
- **SC-008**: 복제본이 있는 샤드의 노드 장애에서 자동 전환이 **30초 이내** 완료된다.
- **SC-009**: 분산 벡터 top-10 검색의 재현율이 단일 노드 정확 결과 대비 **95% 이상**이다.
- **SC-010**: 분산 계층 비활성화 시 단일 노드 벤치마크 성능 차이가 **2% 이내**다.
- **SC-011**: 노드 장애로 인한 불완전 결과가 조용히 반환되는 경우가 **0건**이다(장애 주입
  테스트 100회 기준).
- **SC-012**: 분산 트랜잭션의 원자성이 장애 주입 테스트 **100회에서 100%** 유지된다.

## Assumptions

- 단일 노드 저장 엔진(**001**)의 식별자 인코딩은 샤드 ID를 수용할 수 있는 여유 비트를 갖는다.
- 질의 계획 표현(**003**)은 분산 계획으로 확장 가능한 형태여야 한다. 본 스펙은 그 계획에
  원격 실행 연산자를 추가한다.
- 벡터 검색의 단일 노드 의미론은 **004** 가 정의하고, 본 스펙은 샤드 간 병합을 다룬다.
- 접근 정책의 정의는 **005** 가 하고, 본 스펙은 분산 실행에서의 강제를 보장한다.
- 구현 접근은 기존 PostgreSQL 분산 확장(Citus 등)의 인프라 재사용과 자체 구현 중 하나를
  plan 단계에서 결정한다. 어느 쪽이든 헌법 원칙 I(포크 금지)을 지켜야 한다.
- 초기 목표는 **읽기 복제 → 명시적 파티션 키 샤딩 → 그래프 인지 파티셔닝** 순의 단계적
  제공이다. 첫 릴리스에서 전부 제공하지 않는다.
- 지역 간(geo-distributed) 배포와 다중 리전 일관성은 초기 범위 밖이다.
- 노드 간 시각 동기화는 NTP 수준을 가정하며, 스냅샷 일관성이 이에 의존한다면 그 한계를
  명시한다.
- 목표 클러스터 규모는 초기 16노드, 100억 엣지다.
