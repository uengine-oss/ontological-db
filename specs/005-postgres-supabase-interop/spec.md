# Feature Specification: PostgreSQL/Supabase 상호운용 (PostgreSQL & Supabase Interoperability)

**Feature Branch**: `005-postgres-supabase-interop`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "기반 저장 메커니즘은 PostgreSQL을 사용하고, Supabase와 혼용이 되는 그래프 DB"

## 개요

이 제품이 별도 그래프 DB가 아니라 PostgreSQL 확장인 이유는 단 하나 — **기존 관계형 데이터,
기존 도구, 기존 운영 체계와 한 몸으로 동작**하기 위해서다. 그래프가 별도 사일로가 되는 순간
Neo4j를 쓰는 것과 다르지 않다.

이 스펙은 그 접점을 정의한다: SQL ↔ Cypher 상호 호출, 관계형 테이블과 그래프의 동기화,
Supabase 스택(PostgREST, RLS, Realtime, Auth, 마이그레이션)과의 통합, 그리고 표준 PostgreSQL
운영 도구(백업, 복제, 모니터링)와의 정합.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 그래프와 테이블을 한 질의에서 조인한다 (Priority: P1)

애플리케이션 개발자가 관계형 `orders` 테이블과 그래프의 고객 관계망을 조인해 "친구가 구매한
상품을 아직 사지 않은 고객"을 찾는다. 별도 애플리케이션 코드로 결과를 합치지 않는다.

**Why this priority**: PostgreSQL 위에 있는 이유 그 자체다.

**Independent Test**: 그래프 패턴 + 일반 테이블 조인 질의를 표준 드라이버로 실행하고, 결과
정확성과 실행 계획의 조인 방식을 검증한다.

**Acceptance Scenarios**:

1. **Given** 그래프와 일반 테이블이 같은 데이터베이스에 있고, **When** 하나의 SQL 문에서
   Cypher 패턴 결과와 테이블을 조인하면, **Then** 표준 결과 집합이 반환된다.
2. **Given** 조인 조건이 그래프 쪽 결과를 크게 줄일 때, **When** 계획을 확인하면, **Then**
   조건이 그래프 연산자로 push-down 된다.
3. **Given** 그래프 질의와 테이블 갱신이 같은 트랜잭션에 있을 때, **When** 롤백하면,
   **Then** 양쪽 모두 되돌아간다.
4. **Given** 그래프 결과 컬럼을 SQL 함수와 집계에 사용할 때, **When** 실행하면, **Then**
   표준 PostgreSQL 타입으로 동작한다.

### User Story 2 - 기존 관계형 데이터를 그래프로 노출한다 (Priority: P1)

기존 서비스가 이미 `users`, `follows` 테이블을 운영 중이다. 데이터를 복제하지 않고 이
테이블들을 그래프 노드·엣지로 매핑해 Cypher로 질의한다.

**Why this priority**: 신규 데이터만 그래프로 넣을 수 있다면 도입 장벽이 너무 높다. 점진적
도입 경로가 필요하다.

**Independent Test**: 기존 테이블을 그래프로 매핑하고, 테이블 갱신이 그래프 질의에 즉시
반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 테이블 `users`, `follows` 가 있을 때, **When** 이를 노드·엣지 타입으로
   매핑 선언하면, **Then** 데이터 복사 없이 Cypher로 질의 가능하다.
2. **Given** 매핑된 상태에서, **When** 원본 테이블에 행이 삽입되면, **Then** 다음 그래프
   질의에 즉시 반영된다.
3. **Given** 매핑된 그래프에 Cypher로 쓰기를 시도할 때, **When** 매핑이 읽기 전용으로
   선언되었으면, **Then** 명확한 오류로 거부된다.
4. **Given** 매핑 뷰의 성능이 부족할 때, **When** 네이티브 저장으로 물리화(materialize)하면,
   **Then** 동일한 Cypher 질의가 수정 없이 동작하고 성능이 향상된다.

### User Story 3 - Supabase에서 바로 쓴다 (Priority: P1)

Supabase 프로젝트를 쓰는 개발자가 대시보드에서 확장을 켜고, 프론트엔드에서 PostgREST/
supabase-js로 그래프 질의 결과를 받는다. 별도 서버를 띄우지 않는다.

**Why this priority**: 사용자가 명시적으로 요구한 통합 대상이며, 초기 사용자 획득 경로다.

**Independent Test**: Supabase 로컬 스택(supabase CLI)에 확장을 설치하고 supabase-js로
그래프 질의를 호출하는 종단 테스트를 수행한다.

**Acceptance Scenarios**:

1. **Given** Supabase 인스턴스에서, **When** 확장을 설치하면, **Then** superuser 전용 커널
   기능 없이 설치가 완료된다.
2. **Given** 확장이 설치된 상태에서, **When** supabase-js가 RPC로 그래프 질의를 호출하면,
   **Then** JSON 결과가 반환된다.
3. **Given** Supabase 마이그레이션 파일에 그래프 스키마 DDL이 포함될 때, **When**
   `supabase db push` 를 실행하면, **Then** 스키마가 정상 적용되고 재실행해도 멱등이다.
4. **Given** Supabase Studio에서, **When** 그래프 카탈로그를 조회하면, **Then** 타입 계층과
   통계가 표준 SQL 뷰로 보인다.

### User Story 4 - 행 수준 보안이 그래프에도 적용된다 (Priority: P1)

멀티테넌트 SaaS 운영자가 테넌트 A의 사용자가 테넌트 B의 노드를 절대 볼 수 없게 한다. 트래버설
도중에도 권한 없는 노드를 거쳐가지 못한다.

**Why this priority**: Supabase 사용의 전제 조건이다. 그래프 트래버설은 권한 우회 경로가 되기
쉬워 명시적 설계가 필요하다.

**Independent Test**: 두 테넌트 데이터를 섞어 넣고, 각 역할로 트래버설·집계·경로 질의를
실행해 교차 노출이 없는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 테넌트별 접근 정책이 정의되어 있고, **When** 테넌트 A의 역할로 전체 노드를
   조회하면, **Then** 테넌트 B의 노드가 하나도 반환되지 않는다.
2. **Given** 테넌트 A 노드에서 시작해 테넌트 B 노드를 거쳐 A 노드로 돌아오는 경로가 존재할
   때, **When** A 역할로 3홉 질의를 실행하면, **Then** 그 경로는 반환되지 않는다.
3. **Given** 집계 질의를 실행할 때, **When** 결과를 확인하면, **Then** 접근 불가 노드가
   집계에 포함되지 않아 개수로 존재를 추론할 수 없다.
4. **Given** 정책이 적용된 상태에서, **When** 성능을 측정하면, **Then** 정책 오버헤드가
   문서화된 범위 내에 있고 정책 조건이 그래프 연산자로 push-down 된다.
5. **Given** 관계에 대한 접근 정책이 정의되면, **When** 트래버설을 수행하면, **Then**
   접근 불가 관계를 통한 확장이 차단된다.

---

### User Story 5 - 그래프 변경을 실시간으로 구독한다 (Priority: P2)

프론트엔드가 특정 서브그래프의 변경을 구독해 UI를 갱신한다. Supabase Realtime 또는 PostgreSQL
논리 복제 기반으로 동작한다.

**Why this priority**: 협업 도구·에이전트 대시보드에 필요하지만, 기본 CRUD가 먼저다.

**Independent Test**: 구독을 걸고 그래프를 변경한 뒤 이벤트 수신 지연과 내용 정확성을 측정한다.

**Acceptance Scenarios**:

1. **Given** 특정 타입의 노드 변경 구독이 설정되어 있고, **When** 해당 타입 노드가 생성/수정/
   삭제되면, **Then** 변경 이벤트가 전달된다.
2. **Given** 접근 정책이 적용된 구독에서, **When** 권한 없는 노드가 변경되면, **Then** 그
   이벤트는 전달되지 않는다.
3. **Given** 롤백된 트랜잭션에서, **When** 구독을 확인하면, **Then** 이벤트가 전달되지 않는다.

---

### User Story 6 - 표준 운영 도구가 그대로 통한다 (Priority: P2)

DBA가 기존 절차대로 백업·복원·모니터링·업그레이드를 수행한다. 그래프 때문에 별도 절차를
만들지 않는다.

**Why this priority**: 헌법 원칙 I의 실질적 검증이다.

**Independent Test**: 표준 백업/복원/복제/업그레이드 절차를 그래프 데이터가 있는 상태에서
수행하고 정합성을 검증한다.

**Acceptance Scenarios**:

1. **Given** 그래프 데이터가 있는 데이터베이스에서, **When** `pg_dump` 후 새 인스턴스에
   복원하면, **Then** 모든 그래프 데이터·스키마·인덱스가 재현된다.
2. **Given** 스트리밍 복제가 설정된 상태에서, **When** 그래프를 변경하면, **Then** 대기
   서버에 반영되고 읽기 질의가 정상 동작한다.
3. **Given** PITR 설정에서, **When** 특정 시점으로 복구하면, **Then** 그래프 상태가 그 시점과
   일치한다.
4. **Given** 확장 버전을 업그레이드할 때, **When** `ALTER EXTENSION ... UPDATE` 를 실행하면,
   **Then** 기존 데이터를 재적재하지 않고 완료되거나, 필요한 마이그레이션 절차가 명확히
   안내된다.
5. **Given** 표준 모니터링(pg_stat_statements 등)이 켜져 있을 때, **When** 그래프 질의를
   실행하면, **Then** 통계에 집계된다.

---

### Edge Cases

- **논리 복제**: 그래프 내부 저장 구조가 논리 디코딩에 어떻게 표현되는지 정의 필요.
  최소한 물리 복제는 완전 지원되어야 한다.
- **RLS 우회 위험**: 함수 인터페이스를 통한 그래프 질의가 `SECURITY DEFINER` 로 정책을
  우회하지 않아야 한다.
- **매핑 테이블 스키마 변경**: 매핑된 원본 테이블의 컬럼이 삭제될 때의 동작.
- **순환 참조**: 그래프 → 테이블 → 그래프로 참조가 순환할 때의 트랜잭션 동작.
- **커넥션 풀러(PgBouncer)**: transaction 모드에서 prepared statement 재사용과의 상호작용.
- **확장 버전 불일치**: 복제 주-대기 간 확장 버전이 다를 때의 동작.
- **PostgREST 스키마 캐시**: 그래프 스키마 변경 후 PostgREST 캐시 갱신 필요 여부.

## Requirements *(mandatory)*

### Functional Requirements

**SQL ↔ Cypher 상호운용**

- **FR-001**: 시스템은 SQL 문 안에서 Cypher 패턴 결과를 테이블처럼 참조할 수 있는 문법을
  제공해야 한다.
- **FR-002**: 그래프 질의 결과는 표준 PostgreSQL 타입 또는 문서화된 컴포지트 타입으로
  반환되어 SQL 연산자·함수·집계에 사용 가능해야 한다.
- **FR-003**: SQL 조건 중 그래프 연산자로 내릴 수 있는 것은 push-down 되어야 한다.
- **FR-004**: 시스템은 Cypher 안에서 SQL 서브쿼리 또는 테이블 값을 참조할 수 있어야 한다.
- **FR-005**: 그래프 연산과 관계형 연산은 동일 트랜잭션·동일 스냅샷에서 동작해야 한다.

**관계형 데이터 매핑**

- **FR-006**: 시스템은 기존 테이블을 노드 타입/관계 타입으로 매핑하는 선언을 지원해야 하며,
  데이터 복제를 요구해서는 안 된다.
- **FR-007**: 매핑은 컬럼 → 프로퍼티, 외래키 → 관계, 조인 테이블 → n-ary 관계를 표현할 수
  있어야 한다.
- **FR-008**: 매핑된 그래프는 원본 테이블 변경을 즉시 반영해야 한다.
- **FR-009**: 매핑은 읽기 전용 또는 읽기/쓰기로 선언 가능해야 하며, 읽기 전용 매핑에 대한
  쓰기는 명확한 오류로 거부되어야 한다.
- **FR-010**: 시스템은 매핑된 그래프를 네이티브 저장(001)으로 물리화하는 경로를 제공해야 하며,
  물리화 전후 동일한 Cypher 질의가 동일 결과를 내야 한다.
- **FR-011**: 시스템은 네이티브 그래프를 관계형 뷰(노드 테이블, 엣지 테이블)로 노출해야 하며,
  기존 BI/ETL 도구가 SQL로 읽을 수 있어야 한다.

**보안**

- **FR-012**: 시스템은 노드와 관계 각각에 대한 행 수준 접근 정책을 지원해야 한다.
- **FR-013**: 접근 정책은 트래버설 도중에도 적용되어야 하며, 권한 없는 노드/관계를 경유하는
  경로가 결과에 나타나서는 안 된다.
- **FR-014**: 접근 불가 데이터는 집계·개수·존재 여부로도 추론되어서는 안 된다.
- **FR-015**: 접근 정책 조건은 가능한 한 그래프 연산자로 push-down 되어야 한다.
- **FR-016**: 시스템이 제공하는 함수·뷰는 접근 정책을 우회하는 경로를 만들어서는 안 된다.
- **FR-017**: 시스템은 PostgreSQL 역할·권한 체계(GRANT/REVOKE)를 그래프 객체(그래프, 타입)에
  적용할 수 있어야 한다.

**Supabase 통합**

- **FR-018**: 확장은 Supabase를 포함한 관리형 PostgreSQL 환경에 superuser 전용 커널 기능 없이
  설치 가능해야 한다.
- **FR-019**: 그래프 질의는 PostgREST를 통해 RPC로 호출 가능해야 하며, 결과가 JSON으로
  직렬화되어야 한다.
- **FR-020**: 그래프 스키마 DDL은 Supabase 마이그레이션 파일에 포함 가능해야 하며, 재실행
  시 멱등해야 한다.
- **FR-021**: 그래프 변경 이벤트는 Supabase Realtime 또는 PostgreSQL 논리 복제를 통해 구독
  가능해야 하며, 구독에도 접근 정책이 적용되어야 한다.
- **FR-022**: 그래프 카탈로그는 표준 SQL 뷰로 노출되어 Supabase Studio 등 일반 도구에서 조회
  가능해야 한다.
- **FR-023**: 시스템은 Supabase Auth의 사용자 컨텍스트(`auth.uid()` 등)를 접근 정책에서 사용할
  수 있어야 한다.

**운영 정합성**

- **FR-024**: `pg_dump`/`pg_restore` 로 그래프 데이터·스키마·인덱스가 완전히 백업·복원되어야
  한다.
- **FR-025**: 물리 복제와 PITR이 그래프 데이터에 대해 정상 동작해야 한다.
- **FR-026**: 그래프 질의는 `pg_stat_statements` 등 표준 모니터링 도구에 집계되어야 한다.
- **FR-027**: 확장 업그레이드는 `ALTER EXTENSION ... UPDATE` 로 수행 가능해야 하며, 데이터
  재적재가 필요한 경우 사전에 명시되어야 한다.
- **FR-028**: 시스템은 커넥션 풀러(PgBouncer transaction 모드) 환경에서 정상 동작해야 한다.
- **FR-029**: 시스템은 확장 제거(`DROP EXTENSION`) 시 남는 객체가 없어야 한다.

### Key Entities

- **Graph-Table Mapping**: 기존 테이블을 그래프 타입으로 해석하는 선언. 컬럼 매핑, 키 매핑,
  방향, 읽기/쓰기 모드를 갖는다.
- **Relational View of Graph**: 네이티브 그래프를 노드/엣지 테이블로 보여주는 표준 뷰.
- **Access Policy**: 노드/관계 단위 접근 제어 규칙. 역할, 조건 표현식, 적용 대상 타입을 갖는다.
- **Change Event**: 그래프 변경 구독으로 전달되는 이벤트. 대상, 연산 종류, 이전/이후 값,
  트랜잭션 식별자를 갖는다.
- **Migration Unit**: 마이그레이션 파일에 담기는 멱등한 그래프 스키마 정의.
- **Extension Version**: 확장의 설치 버전과 업그레이드 경로.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 그래프 패턴과 관계형 테이블을 조인하는 질의가 **애플리케이션 코드 없이 단일 SQL
  문**으로 표현되며, 별도 왕복이 발생하지 않는다.
- **SC-002**: 기존 테이블 매핑 방식으로 그래프 질의를 시작하는 데 **데이터 복제가 0바이트**
  필요하다.
- **SC-003**: Supabase 로컬 스택에서 확장 설치 → 스키마 생성 → supabase-js 질의까지의 종단
  시나리오가 **자동 테스트로 통과**한다.
- **SC-004**: 멀티테넌트 격리 테스트에서 교차 테넌트 데이터 노출이 **0건**이며, 경로 우회
  시나리오 100종 모두 차단된다.
- **SC-005**: 접근 정책 적용으로 인한 트래버설 지연 증가가 **30% 이내**다.
- **SC-006**: `pg_dump` → 복원 → 전체 질의 회귀 스위트 실행이 **100% 동일 결과**를 낸다.
- **SC-007**: 스트리밍 복제 대기 서버에서 그래프 읽기 질의가 **주 서버와 동일 결과**를 낸다.
- **SC-008**: 그래프 변경 이벤트의 구독 전달 지연 p95가 **1초 이내**다.
- **SC-009**: 기존 PostgreSQL 클라이언트 라이브러리 **3종 이상**에서 코드 수정 없이 그래프
  질의와 결과 처리가 가능하다.
- **SC-010**: `DROP EXTENSION` 후 잔여 객체가 **0개**다.

## Assumptions

- Cypher 문법과 계획·실행은 스펙 **003-cypher-query-engine** 이 담당하며, 본 스펙은 SQL 접점의
  문법과 의미론을 확정한다.
- 네이티브 저장 구조는 스펙 **001-graph-storage-engine** 이며, 본 스펙의 관계형 뷰는 그 위의
  논리적 노출이다.
- 대상 Supabase 환경은 셀프호스트 및 클라우드 모두를 포함한다. 다만 Supabase 클라우드의 확장
  허용 목록 등재는 외부 승인 절차이므로 본 스펙의 성공 기준은 "셀프호스트/로컬 스택에서 동작"
  으로 정의하고, 클라우드 등재는 별도 과제로 추적한다.
- 논리 복제에서 그래프 내부 구조의 표현 방식은 초기 릴리스에서 완전 지원 대신 "물리 복제 완전
  지원 + 변경 이벤트 스트림 제공"으로 대체할 수 있다.
- 접근 정책의 표현은 PostgreSQL RLS 정책 문법을 최대한 재사용한다.
- 분산 배포에서의 상호운용은 스펙 **007-distributed-cluster** 범위다.
