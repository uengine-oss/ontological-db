# Feature Specification: TypeQL 질의 표면 (TypeQL Query Surface)

**Feature Branch**: `010-typeql-query-surface`

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "typedb 쿼리도 동작하는지 확인바람. 구현이 안되었다면 스펙킷으로 스펙추가하고 typedb 에 있는 예제 애플리케이션으로 테스트도 해줘."

## 개요

스펙 002는 TypeDB의 **개념 모델**(entity/relation/attribute, role, 다중 상속, 구간 라벨링
상속 인덱스)을 벤치마킹해 카탈로그로 구현했다. 그러나 002의 Assumptions는 이렇게 못박았다:

> "TypeDB의 TypeQL 문법 자체를 채택하지는 않으며, Cypher 확장 문법으로 표현한다."

그 결과 오늘 이 데이터베이스는 **TypeDB의 모델은 갖되 TypeDB의 언어는 갖지 않는다**.
`og_cypher()`는 있고 `og_typeql()`은 없다. TypeDB 사용자가 가진 스키마 파일(`.tql`),
적재 스크립트, 질의문은 한 줄도 그대로 실행되지 않는다.

이 스펙은 그 간극을 닫는다. **TypeQL(TypeDB 3.x 문법)을 1급 질의 표면으로 추가**하여,
TypeDB에서 쓰던 자산을 수정 없이 가져와 이 엔진 위에서 실행할 수 있게 한다.

핵심 주장은 성능이 아니라 **이식성(portability)**이다. 002가 "TypeDB급 타입 시스템"을
주장했다면, 이 스펙은 그 주장을 **TypeDB의 실제 예제 애플리케이션을 그대로 돌려서** 검증한다.
헌법 원칙 X("Benchmarked or It Didn't Happen")의 적합성 판(版)이다.

이것은 Cypher를 대체하지 않는다. 두 언어는 같은 그래프, 같은 카탈로그, 같은 저장 엔진을
공유하며 하나의 트랜잭션 안에서 섞여 실행될 수 있다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - TypeDB 스키마 파일이 수정 없이 적재된다 (Priority: P1)

TypeDB를 쓰던 팀이 자신의 `schema.tql`을 그대로 가져온다. `define` 블록 하나를 실행하면
entity/relation/attribute 타입, 상속(`sub`), 소유(`owns`), 역할(`relates`/`plays`),
애너테이션(`@key`, `@unique`, `@card`, `@abstract`, `@values`, `@range`)이 모두 카탈로그에
반영된다. 반영 결과는 기존 스키마 introspection으로도, TypeQL 스키마 덤프로도 확인할 수 있다.

**Why this priority**: 스키마를 적재하지 못하면 나머지 모든 것이 무의미하다. 이식성의 첫 관문이다.

**Independent Test**: TypeDB 공식 예제(bookstore)의 `schema.tql`을 한 글자도 고치지 않고
실행한 뒤, 정의된 타입 수·상속 관계·역할·소유 관계가 원본 스키마와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 빈 그래프에서, **When** bookstore `schema.tql`의 `define` 블록을 실행하면,
   **Then** 오류 없이 완료되고 entity 15개·relation 10개·attribute 21개와 그 상속 관계가
   카탈로그에 생성된다.
2. **Given** `entity hardback sub book`이 정의된 상태에서, **When** 상속을 조회하면,
   **Then** `hardback`은 `book`의 서브타입이며 `book`이 선언한 `owns`/`plays`를 모두 상속한다.
3. **Given** `relation authoring sub contribution, relates author as contributor`가 정의될 때,
   **When** 역할을 조회하면, **Then** `author`는 `contributor` 역할을 특수화한 역할로 기록된다.
4. **Given** `attribute status value string @values("pending", "paid", ...)`가 정의될 때,
   **When** 허용되지 않은 값을 적재하면, **Then** 거부되고 허용 목록이 오류에 포함된다.
5. **Given** 이미 정의된 스키마에서, **When** 같은 `define`을 다시 실행하면, **Then**
   중복 생성 없이 멱등하게 성공한다.

### User Story 2 - TypeDB 데이터 파일이 수정 없이 적재된다 (Priority: P1)

같은 팀이 자신의 `data.tql`을 가져온다. `insert`, `match ... insert`, `put`이 섞인 수백 개의
질의 블록이 순서대로 실행되어 엔티티·관계·속성이 생성된다. 속성은 TypeDB와 같이 **값이 같으면
같은 인스턴스**로 취급되어 공유된다.

**Why this priority**: 스키마만으로는 아무것도 질의할 수 없다. 적재는 이식성의 두 번째 관문이며,
`put`(있으면 재사용, 없으면 생성) 의미론은 TypeDB 적재 스크립트의 필수 관용구다.

**Independent Test**: bookstore `data.tql`을 그대로 실행한 뒤, 엔티티/관계/속성 인스턴스 수를
세어 원본 파일이 서술하는 수와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 스키마가 적재된 그래프에서, **When** `insert $c isa country, has name "United States";`를
   실행하면, **Then** country 인스턴스 1개와 name 속성 1개가 생성되고 연결된다.
2. **Given** 두 책이 같은 장르 문자열을 가질 때, **When** 각각 `has genre "fiction"`으로 적재되면,
   **Then** 두 책은 **동일한** genre 속성 인스턴스를 공유한다.
3. **Given** `match $city isa city, has name "London"; insert ... (location: $city, located: $pub) isa locating;`
   를 실행하면, **Then** 매치된 각 바인딩마다 관계 인스턴스가 생성되고 역할 배정이 기록된다.
4. **Given** `put $c isa contributor, has name "Adams, Douglas";`를 두 번 실행하면, **Then**
   contributor 인스턴스는 하나만 존재한다.
5. **Given** 3항 관계 `(published: $b, publisher: $p, publication: $pub) isa publishing`를 적재하면,
   **Then** 세 역할 배정이 모두 보존되고 역할 이름으로 되찾을 수 있다.
6. **Given** 관계가 속성을 소유하는 `(...) isa order-line, has quantity 2`를 적재하면,
   **Then** 관계 인스턴스가 속성을 소유한 상태로 저장된다.

### User Story 3 - TypeDB 질의가 문서에 적힌 결과를 그대로 낸다 (Priority: P1)

적재된 데이터 위에서 예제 애플리케이션 문서에 실린 질의를 실행한다. 패턴 매칭(`isa`, `has`,
역할 기반 관계 패턴), 비교 술어, 다형성(추상 타입으로 질의하면 서브타입이 모두 응답),
`fetch`(중첩 서브페치 포함)가 동작하고, 결과 JSON이 문서의 결과와 **집합적으로 동일**하다.

**Why this priority**: 이 스펙의 가치 주장 전체가 여기서 검증된다. 적재만 되고 질의가 다르면
이식성은 없는 것이다.

**Independent Test**: 예제 문서에 결과 JSON이 함께 실린 질의를 실행하고, 순서를 무시한 집합
비교로 문서 결과와 일치하는지 검증한다.

**Acceptance Scenarios**:

1. **Given** bookstore 데이터에서, **When** `match $book isa book, has genre "science fiction"; fetch { "title": $book.title, "authors": [...], "price": $book.price };`를
   실행하면, **Then** 문서에 실린 두 건(제목·저자·가격)이 그대로 반환된다.
2. **Given** 추상 타입 `book`으로 질의할 때, **When** 데이터에는 hardback/paperback/ebook만
   존재하면, **Then** 세 서브타입 인스턴스가 모두 응답한다(다형성).
3. **Given** `match $promotion isa promotion, has start-timestamp <= $time, has end-timestamp >= $time;`
   처럼 비교 술어가 있을 때, **When** 실행하면, **Then** 기간에 걸친 프로모션만 반환된다.
4. **Given** `fetch`에 산술식(`round(100 * $p * (1 - $d)) / 100`)이 포함될 때, **When**
   실행하면, **Then** 문서에 적힌 최종 가격이 계산되어 반환된다.
5. **Given** 저자가 없는 책이 있을 때, **When** 서브페치 목록으로 저자를 요청하면, **Then**
   그 책도 빈 목록과 함께 반환된다(서브페치는 결과를 제거하지 않는다).
6. **Given** 역할 이름을 생략한 관계 패턴 `($review, $product) isa rating;`을 쓸 때,
   **When** 실행하면, **Then** 역할 배정 가능한 조합이 모두 매칭된다.

### User Story 4 - 질의 파이프라인과 쓰기 질의가 동작한다 (Priority: P2)

`select`, `sort`, `limit`, `offset`, `distinct`, `reduce`(집계, `groupby`)로 결과를 다듬고,
`match ... delete`, `match ... update`로 데이터를 수정한다. 여러 단계를 연결한 파이프라인이
TypeDB와 같은 순서 의미론으로 실행된다.

**Why this priority**: 읽기 전용 이식은 절반의 이식이다. 다만 P1 세 편이 성립해야 의미가 있다.

**Independent Test**: 각 스테이지를 단독으로 검증하는 회귀 질의를 실행하고, 파이프라인 순서를
바꿨을 때 결과가 정의대로 달라지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 다수의 책이 있을 때, **When** `sort $price desc; limit 3;`을 적용하면, **Then**
   가장 비싼 3권이 가격 내림차순으로 반환된다.
2. **Given** 주문과 주문라인이 있을 때, **When** `reduce $n = count groupby $order;`를 실행하면,
   **Then** 주문별 라인 수가 반환된다.
3. **Given** `match $b isa book, has genre "obsolete"; delete $b;`를 실행하면, **Then** 해당
   책과 그 책이 참여한 관계 인스턴스가 정합성을 깨지 않고 제거된다.
4. **Given** `match $b isa book, has stock $s; update $b has stock 0;`을 실행하면, **Then**
   기존 stock 소유가 대체된다.
5. **Given** `limit` 뒤에 `sort`가 오는 파이프라인과 그 반대 순서를 각각 실행하면, **Then**
   두 결과가 서로 다르며 각각 TypeDB 의미론과 일치한다.

---

### User Story 5 - 두 언어가 하나의 그래프를 공유한다 (Priority: P2)

TypeQL로 적재한 데이터를 Cypher로 질의하고, Cypher로 만든 데이터를 TypeQL로 질의한다.
같은 트랜잭션 안에서 두 언어를 섞어 쓸 수 있고, 어느 언어로 만들었든 감사 로그·이력·벡터
검색·RDF 덤프 같은 기존 기능이 동일하게 적용된다.

**Why this priority**: 이 제품의 차별점은 "TypeQL도 된다"가 아니라 "**한 데이터베이스 안에서**
둘 다 된다"이다. 다만 P1이 없으면 성립하지 않는다.

**Independent Test**: TypeQL로 적재한 bookstore 그래프에 Cypher 질의를 실행해 같은 사실을
얻고, 감사 로그에 두 언어가 각각 기록되었는지 확인한다.

**Acceptance Scenarios**:

1. **Given** TypeQL로 적재한 그래프에서, **When** 동등한 Cypher 질의를 실행하면, **Then** 같은
   사실 집합을 얻는다.
2. **Given** 두 언어의 질의를 실행한 뒤, **When** 감사 로그를 조회하면, **Then** 각 항목의
   언어 구분(`typeql` / `cypher`)과 소요 시간·행 수가 기록되어 있다.
3. **Given** TypeQL 질의가 실패할 때, **When** 오류를 확인하면, **Then** 위치(행/열)와 원인,
   그리고 교정 힌트가 스펙 008의 교정 가능한 오류 형식으로 제공된다.

### User Story 6 - 사용자 정의 함수 (Priority: P3)

스키마에 선언된 `fun` 함수를 질의에서 호출한다. 단일 값 반환 함수와 스트림 반환 함수를
`let $x = f(...)` / `let $x in f(...)`로 사용한다.

**Why this priority**: TypeDB 3.x 스키마에 흔히 등장하지만, 함수 없이도 스키마 적재·데이터
적재·대다수 질의가 성립한다. 재귀 함수는 별도 과제다(Assumptions 참조).

**Independent Test**: bookstore 스키마의 비재귀 함수를 호출하는 문서 질의를 실행해 문서 결과와
비교한다.

**Acceptance Scenarios**:

1. **Given** 스키마에 `fun` 선언이 있을 때, **When** `define`을 실행하면, **Then** 함수 시그니처와
   본문이 보존되고 스키마 덤프에 다시 나타난다.
2. **Given** 비재귀 단일값 함수가 정의된 상태에서, **When** `let $d = best_discount_for_item($book, $t);`
   를 호출하면, **Then** 문서에 적힌 값이 반환된다.
3. **Given** 재귀 함수를 호출하면, **When** 실행하면, **Then** 지원하지 않음을 명시한 오류가
   조용한 오답 대신 반환된다.

---

### Edge Cases

- 스키마에 없는 타입/역할/속성을 참조하면? → 실행 전에 거부하고, 가장 가까운 이름을 제안한다.
- 관계 패턴의 역할 배정이 모호할 때(역할 이름 생략, 후보가 여럿)? → 가능한 모든 배정을 매칭하되,
  플레이어 타입 제약으로 불가능한 조합은 제거한다.
- `@key` 속성이 중복 적재되면? → 거부하고 충돌한 기존 인스턴스를 오류에 포함한다.
- `@card` 상한을 넘겨 소유하면? → 거부한다. 하한 미달은 트랜잭션 커밋 시점에 검사한다.
- 추상 타입을 직접 인스턴스화하면? → 거부한다.
- 같은 값의 속성을 서로 다른 두 트랜잭션이 동시에 생성하면? → 하나의 인스턴스로 수렴한다.
- 속성 인스턴스를 아무도 소유하지 않게 되면? → 고아 속성으로 남지 않도록 정리된다.
- 값 타입이 맞지 않는 비교(`문자열 < 정수`)? → 실행 전에 타입 오류로 거부한다.
- 매우 큰 `.tql` 파일(수천 블록)? → 블록 단위로 스트리밍 실행되며 전체를 메모리에 담지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**언어 표면**

- **FR-001**: 시스템은 TypeQL 질의 문자열을 받아 실행하는 단일 진입점을 제공해야 하며, 결과를
  행 단위 JSON으로 반환해야 한다.
- **FR-002**: 시스템은 실행 없이 TypeQL을 검증하는 진입점을 제공해야 하며, 구문/스키마 오류를
  행·열 위치와 함께 보고해야 한다.
- **FR-003**: 시스템은 읽기 질의가 컴파일된 결과를 열람할 수 있게 해야 한다(Cypher의 동등 기능과
  같은 수준의 투명성).
- **FR-004**: 시스템은 여러 질의 블록이 담긴 스크립트를 순서대로 실행할 수 있어야 하며, 블록
  구분자를 인식해야 한다.
- **FR-005**: 시스템은 주석을 무시해야 한다.

**스키마 정의(define)**

- **FR-006**: 시스템은 entity/relation/attribute 타입 정의를 지원해야 한다.
- **FR-007**: 시스템은 `sub`를 통한 타입 상속을 지원해야 하며, 상속된 소유·역할·플레이 선언이
  서브타입에서 유효해야 한다.
- **FR-008**: 시스템은 `owns`(소유), `relates`(역할 선언), `plays`(역할 수행) 선언을 지원해야 한다.
- **FR-009**: 시스템은 역할 특수화(`relates X as Y`)를 지원해야 한다.
- **FR-010**: 시스템은 attribute 타입의 값 타입(문자열/정수/실수/불리언/날짜시간/날짜/기간/십진수)을
  지원해야 한다.
- **FR-011**: 시스템은 `@abstract`, `@key`, `@unique`, `@card(n..m)`, `@values(...)`, `@range(..)`
  애너테이션을 지원하고 그 제약을 적재 시점에 강제해야 한다.
- **FR-012**: 시스템은 `define`을 멱등하게 실행해야 하며, 동일 정의의 재실행이 실패하지 않아야 한다.
- **FR-013**: 시스템은 스키마를 TypeQL 문법으로 다시 덤프할 수 있어야 한다.
- **FR-014**: 시스템은 스키마 변경 시 스키마 버전을 증가시켜야 한다(스펙 002/008의 캐시 무효화 키).

**데이터 적재(insert / put)**

- **FR-015**: 시스템은 `insert`로 엔티티·관계·속성 인스턴스를 생성할 수 있어야 한다.
- **FR-016**: 시스템은 속성 인스턴스를 **값 기준으로 중복 제거**해야 한다. 같은 타입·같은 값은
  하나의 인스턴스이며 여러 소유자가 공유한다.
- **FR-017**: 시스템은 하나의 소유자가 같은 속성 타입의 값을 여럿 소유하는 것을 지원해야 한다.
- **FR-018**: 시스템은 역할 이름을 명시한 관계 생성과 3개 이상 역할을 갖는 관계를 지원해야 한다.
- **FR-019**: 시스템은 관계 인스턴스가 속성을 소유하고 다른 관계의 역할을 수행하는 것을 지원해야 한다.
- **FR-020**: 시스템은 `match ... insert`에서 매치된 각 바인딩마다 삽입을 수행해야 한다.
- **FR-021**: 시스템은 `put`(존재하면 재사용, 없으면 생성)을 지원해야 한다.

**패턴 매칭(match)**

- **FR-022**: 시스템은 `isa`로 타입 인스턴스를 매칭해야 하며, **서브타입을 자동 포함**해야 한다.
  정확 타입만 요구하는 형태(`isa!`)도 지원해야 한다.
- **FR-023**: 시스템은 `has`로 속성 소유를 매칭해야 하며, 값 리터럴·변수·비교 술어를 모두 받아야 한다.
- **FR-024**: 시스템은 속성 타입 상속을 매칭에 반영해야 한다(상위 속성 타입으로 질의하면 하위
  속성 인스턴스가 응답).
- **FR-025**: 시스템은 역할 이름을 명시한 관계 패턴과 생략한 관계 패턴을 모두 지원해야 한다.
- **FR-026**: 시스템은 비교 술어(`==`, `!=`, `<`, `<=`, `>`, `>=`)와 문자열 술어(`like`, `contains`)를
  지원해야 한다.
- **FR-027**: 시스템은 논리 조합(`;` 결합, `{...} or {...}` 분리, `not {...}` 부정)을 지원해야 한다.
- **FR-028**: 시스템은 `let`으로 값·표현식을 변수에 묶는 것을 지원해야 한다.
- **FR-029**: 시스템은 타입 변수 질의(`$t sub <type>`, `$t label <name>`)를 지원해야 한다.
- **FR-030**: 시스템은 매칭을 관계형 질의로 컴파일해 질의 계획기가 조인 순서를 선택하게 해야 한다.
- **FR-031**: 시스템은 상속 판정에 스펙 002의 구간 라벨링 인덱스를 사용해야 하며 재귀 순회를
  사용하지 않아야 한다.

**결과 성형(pipeline)**

- **FR-032**: 시스템은 `select`, `sort`(asc/desc), `limit`, `offset`, `distinct`를 지원해야 한다.
- **FR-033**: 시스템은 `reduce`와 집계 함수(`count`, `sum`, `max`, `min`, `mean`, `std`, `list`)를
  지원하고 `groupby`를 지원해야 한다.
- **FR-034**: 시스템은 `fetch`로 JSON 문서를 구성해야 하며, 속성 투영(`$x.attr`), 중첩 객체,
  중첩 서브페치 목록, 산술/함수 표현식을 지원해야 한다.
- **FR-035**: 서브페치는 결과 행을 제거하지 않아야 한다(빈 목록으로 반환).
- **FR-036**: 시스템은 파이프라인 스테이지를 선언된 순서대로 적용해야 한다.

**데이터 수정(delete / update)**

- **FR-037**: 시스템은 `match ... delete`로 인스턴스·소유·역할 배정을 삭제할 수 있어야 한다.
- **FR-038**: 시스템은 인스턴스 삭제 시 그것이 참여한 관계와 소유를 정합적으로 정리해야 한다.
- **FR-039**: 시스템은 `match ... update`로 소유를 대체할 수 있어야 한다.

**통합**

- **FR-040**: TypeQL로 만든 데이터는 Cypher로 질의 가능해야 하며, 그 역도 성립해야 한다.
- **FR-041**: 시스템은 TypeQL 질의를 감사 로그에 언어 구분과 함께 기록해야 한다.
- **FR-042**: 시스템은 TypeQL 오류를 스펙 008의 교정 가능한 오류 형식(원인 + 힌트)으로 제공해야 한다.
- **FR-043**: 시스템은 TypeQL 데이터 모델이 기존 저장 구조에 어떻게 대응되는지 문서화된 뷰로
  제공해야 한다.

**함수(P3)**

- **FR-044**: 시스템은 `fun` 선언을 파싱해 보존하고 스키마 덤프에 재현해야 한다.
- **FR-045**: 시스템은 비재귀 함수 호출(`let $x = f(...)`, `let $x in f(...)`)을 평가해야 한다.
- **FR-046**: 시스템은 재귀 함수 호출에 대해 지원하지 않음을 명시적으로 오류로 알려야 하며,
  부분적·조용한 오답을 반환해서는 안 된다.

### Key Entities

- **TypeQL 질의**: 하나 이상의 스테이지로 구성된 파이프라인. 스키마 스테이지(`define`)와
  데이터 스테이지(`match`/`insert`/`put`/`delete`/`update`)와 성형 스테이지(`select`/`sort`/
  `limit`/`offset`/`reduce`/`fetch`)로 나뉜다.
- **타입 선언**: 종류(entity/relation/attribute), 이름, 상위 타입, 소유 목록, 역할 목록,
  수행 역할 목록, 애너테이션 집합.
- **속성 인스턴스**: 타입과 값으로 식별되는 공유 가능한 값 객체. 동일 타입·동일 값은 동일 인스턴스.
- **관계 인스턴스**: 역할 이름 → 플레이어 집합의 배정을 갖는 1급 객체. 속성을 소유할 수 있고
  다른 관계의 역할을 수행할 수 있다.
- **역할**: 관계 타입이 선언한 참가 슬롯. 상위 역할을 특수화할 수 있으며 플레이어 타입 제약을 갖는다.
- **함수**: 이름, 인자 시그니처, 반환 타입(단일/스트림), 본문 파이프라인.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: TypeDB 공식 예제 애플리케이션의 스키마 파일이 **한 글자도 수정하지 않고** 적재된다.
- **SC-002**: 같은 예제의 데이터 파일이 **한 글자도 수정하지 않고** 전부 적재되며, 적재 후
  인스턴스 수가 원본이 서술하는 수와 일치한다.
- **SC-003**: 예제 문서에 결과가 함께 실린 질의 중, 함수를 사용하지 않는 질의는 **100%**가
  문서와 동일한 결과(순서 무시 집합 비교)를 반환한다.
- **SC-004**: 추상 타입으로 던진 질의가 모든 서브타입 인스턴스를 반환한다(다형성 검증 100%).
- **SC-005**: TypeQL로 적재한 그래프에 대해 동등한 Cypher 질의가 같은 사실 집합을 반환한다.
- **SC-006**: 스키마를 덤프해 새 그래프에 다시 적재하면 원본과 동일한 스키마가 재구성된다
  (왕복 무손실).
- **SC-007**: 잘못된 TypeQL 질의는 **실행 전에** 거부되며, 오류 메시지에 위치와 교정 힌트가
  포함된다(부분 실행으로 인한 데이터 오염 0건).
- **SC-008**: 지원하지 않는 구문은 조용히 무시되지 않고 명시적 오류를 낸다(무언의 오답 0건).
- **SC-009**: 예제 애플리케이션 전체(스키마 적재 → 데이터 적재 → 문서 질의 실행 → 결과 비교)가
  단일 명령으로 재현 가능한 회귀 스위트로 실행된다.
- **SC-010**: 지원 범위와 미지원 범위가 문서에 명시되며, 미지원 항목은 "부분은 부분"이라고
  적힌다(헌법 원칙, README의 상태 표기 규칙).

## Assumptions

- 대상 문법은 **TypeDB 3.x TypeQL**이다. 2.x 문법(`get`, `rule`, `then`/`when`)은 초기 범위가
  아니며, 만나면 명시적 오류를 낸다.
- 검증에 쓰는 예제 애플리케이션은 TypeDB 공식 예제 저장소의 **bookstore**(TypeDB 3.0 스키마 +
  샘플 데이터 + 문서화된 예제 질의)다. 결과가 문서에 함께 실려 있어 외부 근거로 쓸 수 있기
  때문이다.
- 이 스펙은 새로운 저장 구조를 도입하지 않는다. 스펙 001의 노드·간선·인접 세그먼트와 스펙 002의
  타입 카탈로그·역할·구간 라벨링 인덱스 위에 매핑한다. 구체적 매핑은 계획 단계에서 정한다.
- 속성을 값 기준으로 공유하는 TypeDB 의미론을 채택한다. 이는 Cypher의 프로퍼티 의미론과 다르며,
  두 모델이 한 그래프에 공존할 때의 표현 방식은 계획 단계에서 정의하고 FR-043으로 문서화한다.
- **재귀 함수와 스트림 함수의 완전한 평가는 초기 범위가 아니다.** 이는 사실상 재귀 질의 계층이며
  독립된 과제다. 비재귀 함수부터 시작한다.
- TypeDB의 트랜잭션 종류 구분(schema / write / read 트랜잭션)은 채택하지 않는다. PostgreSQL의
  트랜잭션이 그 역할을 하며, 이는 헌법 원칙 IX(호스트의 MVCC를 그대로 쓴다)와 일치한다.
- TypeDB 네트워크 프로토콜·드라이버 호환은 범위 밖이다. 이 스펙은 **언어** 호환이지 **와이어**
  호환이 아니다.
- 성능 목표는 이 스펙의 1차 관심사가 아니다. 이식성이 먼저이며, TypeQL 경로의 성능 특성은
  스펙 009의 하네스로 별도 측정한다.
