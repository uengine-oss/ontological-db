What the numbers say

Neo4j is the traversal number to beat

Neo4j answers the three-hop question in against our — faster — and its latency barely responds to scale. At one and two hops this benchmark cannot see its engine at all: the measured time is at the protocol floor, the cost of an empty query through the same client. Read the floor row of every table before comparing across transports.

Apache AGE collapses on *1..n, not on storage

The headline gap against AGE is real but it is not a storage result. Asked the same question as a union of fixed-length patterns — exactly what TypeQL forces TypeDB to do — AGE answers instead of , a factor of . Its one-hop and property-scan times are competitive with everyone here. What fails is the variable-length path operator: the expansion runs inside a function scan the planner cannot see into, and the terminal node is then rejoined against a full scan of the vertex table.

AGE also creates no index on edge endpoints or properties as installed. Every system in these tables was given the indexes its own documentation calls for; benchmarking AGE without them measures a misconfiguration.

TypeDB finds fastest and writes slowest

TypeDB has the quickest single-hop and one of the quickest property lookups here — a @key lookup goes straight to the attribute object. Traversal is where the type system stops helping: TypeQL has no *1..n, so bounded depth must be written as a disjunction that re-walks its own prefixes. Loading the million-edge graph took against for Neo4j.

The plain-SQL floor is still hard to beat

Two indexed tables and a recursive CTE — no query engine, no schema, no Cypher — win nearly every cell. That row is in the table on purpose. Anything in this comparison has to justify itself against it, not against the other products.

What this does not show

  • One machine, one process, no concurrency — every query ran alone.
  • Two scales of one graph shape: uniform random, fixed average degree. No hubs, no skew.
  • Four read queries. No writes under measurement, no shortest path, no LDBC SNB.
  • Community and default configurations; no engine was tuned for this workload.
  • Warm cache throughout; cold start is not measured.
  • Some systems were measured in separate runs against the same seeded graph — the TypeDB load alone takes minutes. Same machine, same edge list, same method; not the same wall-clock minute. Each table names the run every column came from.
