# ★ API 계약 개선 포인트

> **이 문서가 답하는 질문**
> - 이 API 계약면에서 가장 위험한 것은 무엇인가?
> - 어떤 함수가 서로 일관되지 않고, 왜 그것이 비용인가?
> - 오류가 클라이언트에게 어떻게 잘못 전달되는가?
> - 버전 호환과 폐기 경로는 어떻게 되어 있는가?
> - 미구현 기능이 사용자에게 정직하게 보고되는가?

## 0. 요약 — 상위 5건

| 순위 | ID | 제목 | 왜 이것이 1순위인가 |
|---|---|---|---|
| 1 | **API-01** | Cypher `UNION`이 조용히 결과를 잘라낸다 | 오류 없이 **틀린 답**을 준다. 계약 위반 중 유일하게 정답성을 해친다 |
| 2 | **API-29** | Studio `POST /api/sql`이 인증 없이 임의 SQL을 실행 | 서버에 도달 가능한 누구든 DB 전권 |
| 3 | **API-31** | SQLSTATE 규율 부재 — 모든 오류가 `XX000` | 클라이언트가 재시도 가능 여부를 판단할 수 없다 |
| 4 | **API-10** | `og_explain_error`가 라벨 오타를 못 잡는다 (`UNKNOWN_LABEL` 도달 불가) | 에이전트 자가 교정의 핵심 기능이 가장 흔한 실수에 무력 |
| 5 | **API-05** | 세 함수가 SQL 조각을 그대로 보간 — 신뢰 경계 미문서화 | `filter` / `policy_expr` / `source_table` |

## 2. 우선순위 제안 (의존 관계 포함)

```
API-32 (버전/폐기 경로)  ──┐
                           ├─→ 시그니처를 바꾸는 모든 항목의 전제
API-31 (SQLSTATE)      ──┼─→ API-10, API-28(d), API-30(b) 의 전제
                           │
API-01 (UNION)         ────┘   ← 전제 없이 즉시 가능 (거부만 추가)
API-29 (Studio 인증)   ────    ← 전제 없이 즉시 가능
API-23 (데이터 손실)   ────    ← 전제 없이 즉시 가능 (force 인자)
```

**즉시 착수 가능(파괴적 변경 없음)**: API-01(거부만), API-05(문서+검증), API-06,
API-09, API-12, API-16, API-19(거부만), API-20(NOTICE), API-22(문서), API-24,
API-25, API-27, API-29, API-23(force 인자 추가)

**API-32 이후**: API-03, API-08, API-11, API-15, API-30(a)

**API-31 이후**: API-10, API-28(d), API-30(b)
